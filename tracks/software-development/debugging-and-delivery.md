# 调试与真实交付

中文 | [English](debugging-and-delivery.en.md)

## 业务承诺先于测试工具

调试前先说明用户通过什么正式入口、提供什么真实输入、完成什么工作、得到什么可继续使用的结果。测试章程同时写明环境、质量底线、风险假设、不可逆操作和停止条件。

页面打开、接口返回成功、进程退出、Agent 声称完成、文件非空或截图正常，都不能单独证明业务成立。

## 三个独立证据面

Agent 自主调试需要三个互相校验的面：

1. **行动面**：通过用户或正式调用者真正使用的 UI、CLI、公开 API 或正式 Agent 接口推进业务。
2. **观察面**：只读页面、网络、进程、日志、正式状态、持久化数据和最终产物，确认系统实际发生了什么。
3. **判定面**：按业务承诺检查内容、完整性、来源、可编辑性、持久化、隔离和用户是否能继续使用。

三个面不能依赖同一条成功信号。观察面可以白盒读取，但不能绕过产品入口补数据、改状态或制造通过。产品没有正式机器入口时，不为了测试发明第二套业务 API。

## 自适应测试章程

每轮根据代码变化、上次失败、真实平台和数据选择一条完整主链，以及一到三个最有信息量的风险分支。常见风险包括历史状态升级、中途修改、取消与恢复、断网重开、重复提交、跨主体污染和同一输入的稳定性。

先记录本轮身份：不可变版本、平台、环境、账号或项目、真实输入快照、允许费用和写入边界。同一正式状态只允许一个业务所有者，避免多个实例或 Agent 同时操作后无法归因。

## 执行顺序

1. 用最小静态检查、回归、构建和安装校验排除确定性错误。
2. 从唯一正式入口开始，不直接修改数据库或内部状态。
3. 让业务运行到明确成功、失败或可恢复终态；排队、转圈和暂时无输出都不是终态。
4. 检查最终交付物和正式状态，不只看成功提示。
5. 退出并重开同一对象，验证持久化、恢复和未完成任务没有被静默复制。
6. 主链通过后，再按风险证据攻击最可能失败的边界。

生成式结果不能断言固定文本，也不能只让执行 Agent 自我评价。至少分别检查结构底线、事实底线和业务质量；语义质量可由独立 Reviewer 或人工抽检，但仍要回到真实来源和交付物。

## 失败后保留现场

失败时先保存时间、版本、页面、日志、进程、正式状态和产物，不立即清缓存、换假数据、手工补状态或无限重试。

先区分失败层：环境与权限、安装与版本残留、运行时、业务状态、展示映射或结果质量。UI 显示失败不能自动归因于网络或模型，环境故障也不能直接算产品缺陷。

## 可证伪根因

修改前写出一条能够被实验否定的因果描述：

> 当某个条件发生时，某个正式所有者因为具体机制没有完成应有责任，所以用户看到这个症状。

然后选择最有区分度的控制实验，例如比较正常版本与当前版本、官方入口与包装层、正式状态与 UI 投影、小输入与大输入，或原用户状态与隔离状态。一次实验只区分关键竞争假设，不同时修改多个层。

## 修复责任边界

修复应让正式所有者重新承担完整生命周期：合并重复真源，删除伪成功 fallback，修正输入与写入边界，保留原任务并恢复观察，让正式业务状态驱动界面。

确定性缺陷留下最窄行为回归，证明旧实现失败、新实现通过。随后仍要在同一正式入口、目标平台和真实数据上复测。若同一用户症状再次出现，停止局部补丁，重新检查产品目标、真源和责任所有者。

## 完成条件

- 正式入口完成了真实业务；
- 行动、观察和判定证据能够互相校验；
- 最终产物对用户真实可用；
- 人工修改、费用和关键风险没有丢失或伪造；
- 重开后正式状态与产物保持一致；
- 根因落在正确所有者，并有回归与真实环境复测；
- 未覆盖部分被明确记录，没有用 fallback 或换数据伪装通过。

具体自动化工具、系统命令、日志路径和项目样本属于真实项目实现，不进入本方法。

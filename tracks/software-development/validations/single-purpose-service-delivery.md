# 单用途服务交付验证

中文 | [English](single-purpose-service-delivery.en.md)

## 验证对象

一项已经完成的真实开发与运维任务：在已有共享基础设施上增加一个单用途静态服务，满足外部审核的可访问与可截图要求，同时不得影响原有网络服务和主产品。

真实域名、服务器、配置、命令和业务主体继续由开发运维项目拥有。本记录只保存脱敏后的工作结构和验证结论。

## 实际链路

1. 用户结果被限定为“审核方能从公网访问并检查所需信息”，而不是改造主产品。
2. Handoff 明确现有可复用资产、非目标、不能中断的服务、人工决定和验收入口。
3. 设计复用已有静态服务与入口层，没有新增数据库、后台应用或第二套生产系统。
4. 执行前读取私有配置与现场状态；公共方案没有复制凭证和登录方式。
5. 运行时发现预期的热加载路径不可用，现场证据覆盖了文档假设，改用可回滚的服务重启完成加载。
6. 结果同时检查新服务公网可访问、证书成功、页面字段完整，以及已有服务和主产品未受影响。
7. 现场差异和最终验证回写运行文档，使下一位执行者不需要聊天即可续接。

## 五项测试

### 续接测试：通过

独立 Handoff 提供一句话结果、范围、非目标、权威资料、风险、验收入口、回滚和需要人决定的部分。新的 Agent 无需读取旧聊天即可继续执行或复核。

### 真源测试：通过

方案拥有目标与边界，私有配置拥有访问事实，现场系统拥有当前运行状态，Handoff 拥有当前动作。现场状态与预期不一致时，实际服务状态优先，没有为了维护文档正确而强行执行原方案。

### 结果测试：通过

完成证据不是配置文件存在或命令退出成功，而是新服务通过公网正式入口可访问、证书与页面符合要求，同时两个既有入口保持正常。它覆盖了新增结果和不得发生的回归。

### 反馈测试：通过

加载失败没有被包装成成功，也没有反复重试。失败机制被定位到服务当前控制方式，执行路径随之调整，差异和最终行为进入运行文档，直接改变后续操作。

### 迁移测试：部分通过

用户结果、非目标、现场状态优先、正式入口验收和回滚边界可以迁移到其他开发任务。静态服务、证书工具、共享服务器和外部审核字段是案例特有实现，应留在真实项目。

## 规则去向

### 进入跨领域候选

- 当前执行面应保存目标、已接受基线、下一动作和停止点，而不是完整聊天历史。
- 文档、派生视图和现场实时状态承担不同角色；当前可观察事实优先于旧计划。
- 完成必须通过正式入口和人可检查结果证明，并同时检查明确要求不得破坏的既有结果。

### 留在软件开发线路

- 新状态、服务和抽象必须先通过用户问题、唯一所有者与真实验收组成的变更门。
- 调试需要行动、观察和判定三个独立证据面。
- 同一症状复发或补丁开始制造更多状态时，回到架构责任边界，不继续叠加条件。

### 继续观察

- 强模型自由探索与稳定项目约束之间的最小边界。
- 哪些开发任务必须由独立 Reviewer 复核，哪些可以由同一 Agent 的多证据面充分验收。

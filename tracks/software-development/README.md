# 软件开发线路

## 线路问题

当 Agent 能承担越来越多设计、编码、测试和调试工作时，怎样持续守住用户意图、系统真源、责任边界和真实交付，避免局部补丁、伪完成和项目状态漂移？

这条线路研究跨项目开发治理与真实验收，不保存具体产品架构、服务器资产、网络配置、部署凭证、机器环境或项目运行状态。

## 本地验证场

个人开发与运维仓继续拥有已经形成的开发治理、调试规范、基础设施资料和具体运维记录。各产品仓继续拥有自己的产品事实、架构、Handoff、代码和测试。公共仓只提炼跨项目方法与脱敏验证结论。

## 已观察到的候选主干

- 从一句用户可检查的结果开始，模块、页面和代码量都不能代替目标。
- 项目宪法、产品事实、架构真源、当前 Handoff、运行方法和历史记录承担不同职责，聊天不能成为长期真相。
- 设计追求最小充分正确，而不是对错误方向做最小改动；新增状态、fallback、协议和抽象必须通过真实问题与验收证明。
- 正式业务状态与临时控制面必须分开，同一事实只允许一个权威所有者。
- 调试需要行动、观察和判定三个独立证据面；成功提示、退出码和文件存在都不能单独证明业务完成。
- 修复应恢复正确责任边界并留下回归证据；同一症状反复出现时停止叠加补丁，回到目标、真源和架构设计。
- 完成由正式入口、真实环境、真实数据和用户可继续使用的交付物证明。

这些判断目前属于软件开发线路。服务器清单、网络拓扑、命令、工具版本和具体产品流程不会被提升为公共方法。

## 需要验证

- 新 Agent 能否不依赖旧聊天恢复用户结果、项目真源和当前停止点。
- 强模型自由探索与项目长期约束之间，哪些边界确实提高结果稳定性，哪些已经成为枷锁。
- 真实 E2E、回归测试和人工判断怎样共同证明交付，而不建设第二套测试业务。
- 开发中的真源、反馈和责任原则能否解释知识管理或媒体生产中的同类失败。

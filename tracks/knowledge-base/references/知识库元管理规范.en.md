# Knowledge Base Meta-Management Specification (`v0.2-candidate`)

[中文](知识库元管理规范.md) | English

**Position**: This document defines candidate cross-domain knowledge-base invariants and default strategies. An **invariant** needs only one valid counterexample for demotion or removal, but promotion or addition requires evidence from at least two independent domains. A **strategy** is a default that one real case may override. The specification does not depend on one carrier, platform, or product.

**Candidate status**: This version is `v0.2-candidate`. It does not claim that the cross-domain method is frozen before validation in a second real domain.

**Object definitions**:

- **Content object**: any independently addressable knowledge unit, including a native note, semantic document, structured table, image, media object, or evidence page.
- **Organizing relationship**: a carrier-defined classification or location relationship, including directories, tags, database relations, and links.
- **Shell**: the carrier layer that provides permissions, retrieval, interaction, and invocation.
- A knowledge base consists of content objects and organizing relationships. The shell changes implementation, not method.

**Executor**: the agent that organizes the knowledge base.

**Users**: the knowledge-base owner and the person drafting adaptations.

---

## Rule 0: Preconditions

- Before any organization action, the agent reads this specification and the knowledge base's strategy overrides in full.
- Move an uncovered case into the adjudication area and wait for human judgment. Do not invent a rule when neither the specification nor a strategy override covers it.
- Work in batches and report after each batch. The strategy layer defines the default batch size.

## Chapter 1: Invariants

Demotion or removal needs one valid counterexample. Addition or promotion needs evidence from at least two independent domains.

### 1. Object Boundaries Follow Independent Lifecycles

A content object passes only when it satisfies all three tests:

1. **Standalone test**: A target reader can understand the object's content and applicability when retrieving it alone. The body cannot contain an unresolvable reference such as "above" or "see the previous section." Resolve the reference by including necessary context or by creating a stable readable relationship that the knowledge entry point can locate and open. Use a relationship when including context would create a duplicate source of truth. Include context when the relationship cannot guarantee readback.
2. **Lifecycle test**: The object can be reused, updated, and retired independently. Keep content together when sequence, hierarchy, adjacent tables, or cross-references jointly carry the meaning needed to prove one thing.
3. **No-further-split test**: Stop splitting when another split would remove necessary context or independent reuse value.

Lifecycle determines the object boundary. Length, page count, heading level, and source-file boundaries do not.

### 2. No Distortion

- **Allowed**: Faithful compilation and structural organization may convert Word files, PDFs, web pages, archives, and other source containers into semantic content an agent can use. Preserve row and column relationships when they carry table meaning. Change the encoding or carrier, not the content.
- **Prohibited**: Do not change facts, numbers, meaning, subjects, applicability, limits, or commitments. When current capability cannot preserve them, report the block and its impact instead of degrading silently or inventing a substitute.
- **Verification guard**: A compiled object retains a source reference with the real source name and location. Read it back through the knowledge entry point and verify factual equivalence. Human confirmation is required before irreversible source-information loss.

### 3. One Source of Truth and Retirement

- One effective version owns each piece of knowledge. Keep one exact duplicate and record the merged object's former location.
- Obsolete content must leave active retrieval so that ordinary search no longer returns it as valid knowledge. Record the reason and replacement so the action remains traceable.
- Platform capability and compliance determine whether retirement means archiving, deletion, or external audit retention. An agent cannot delete irreversibly outside those policies.

### 4. Minimally Sufficient Names

- **Name-only test**: Without opening the content, a reader can use the name and logical location to judge the topic and likely relevance to a question. Rename an object that fails.
- Keep the core object and qualifiers needed to distinguish the reuse boundary, such as model, region, validity period, or purpose. Do not remove a word if that removal creates ambiguity or a generic label. Avoid identifiers, timestamps, and tool state with no business meaning.
- **Keyword and semantic retrieval**: Domain-specific terms, including product names, model numbers, regulation numbers, people, and industry terms, appear literally in the name and body for keyword retrieval. Include the most common synonym of a core concept at least once in the body for semantic retrieval.

### 5. Metadata

Each content object carries decidable metadata for **source, date, and status (valid or obsolete)**. The carrier chooses the representation, such as a file header, property field, or database column.

### 6. Two-Level Acceptance

Report **technical write completion** only when all three checks pass:

1. **Retrieval**: The target question locates the object.
2. **Actual readback**: The knowledge entry point returns the object's real content, not a summary, placeholder, or inventory item.
3. **Structural completeness**: Metadata, source reference, and status are present.

Record **validated business reuse** as an independent state after the object succeeds in a later real task. It enters the feedback loop and is not a prerequisite for technical write completion. An object without validated reuse may be used, but cannot participate in cross-task decisions as validated knowledge. Only a real task proves reuse.

### 7. Feedback Loop

Review real query and reuse records periodically, monthly by default. Mark retrieval misses, wrong matches, readback failures, and reuse failures. Repair names, synonyms, object boundaries, merges, and retirement. Revise the specification when the evidence requires it.

### 8. Agent Prohibitions

- Object complexity, action reversibility, and failure impact determine batch size. Chapter 2 provides a default. Validate each batch and stop on failure.
- Perform reversible actions only, except deletion explicitly allowed by platform policy and compliance and confirmed by a person.
- Human confirmation is required for any rewrite that changes facts or commitments rather than faithfully compiling them.

## Chapter 2: Strategy Layer

Any knowledge base may override these defaults with one real case.

| Strategy | Default | Notes |
|---|---|---|
| Directory depth | At most 3 levels | Applies only to directory-based carriers. Tags and relational database carriers do not use this rule. |
| Naming format | `topic-keyword-status` | A default template. Any format that passes the name-only test may replace it. |
| Text length | 300 to 2,000 Chinese characters | A warning. Review the object boundary outside the range; do not force a split. |
| Text split | One question per object | A default for text knowledge: the title can become one specific question. Evidence components still follow lifecycle tests. |
| Batch size | At most 10 objects | Adjust for object complexity and failure impact. The invariant is validate each batch and stop on failure. |
| Adjudication area | `inbox/` | Directory-based default. Other carriers use an equivalent mechanism. |
| Obsolete area | `graveyard/` plus an obsolete prefix | Directory-based default. Deletion and audit retention follow platform capability and compliance. |
| Review cycle | Monthly | Adjust to the business cadence. |
| Logical organization | By problem domain | Department, source, and file format are prohibited defaults. A deviation needs evidence because this rule currently has invariant status. |

## Chapter 3: Adaptation

This chapter replaces the mandatory industry customization in `v0.1`.

The adaptation axis is a falsifiable hypothesis. Adapting by industry, task, or knowledge type, or not adapting, are all hypotheses. None is correct by default.

1. **No adaptation by default**: Deploy Chapter 1 invariants and Chapter 2 strategies without pre-adaptation.
2. **Adaptation triggered by evidence**: Adapt only when the same class of problem fails repeatedly; the failure comes from a stable domain-method gap rather than material, permissions, or host capability; the gap cannot be derived from general rules; and the trigger point is explicit.
3. **Smallest adaptation**: Add only the smallest rule that repairs the proven gap, and keep it as a decidable test without untested adjectives.
4. **Industry classification needs evidence**: Adapt by industry only when real data shows that industry labels reliably improve correctness. An industry label does not decide how to process a task that mixes parameter tables, architecture diagrams, pricing, and people.
5. **Calibration**: Test retrieval with 20 to 50 real questions as the minimum. Freeze deployment only after actual readback and real-task reuse complete both acceptance levels in Chapter 1, Section 6.

## Chapter 4: Revising This Specification

- **Demote or remove an invariant**: one valid counterexample is enough. A valid counterexample is reproducible, recorded, and caused by the rule itself rather than missing material, permissions, or host capability.
- **Add or promote an invariant**: requires practical evidence from at least two independent domains.
- **Change a strategy or default**: one real case is enough.
- **For every revision**: archive the old version under `archive/` and record the evidence and source domain in version history.
- **Candidate status**: the current invariant set remains a candidate until validation in a second real domain.

## Chapter 5: Rejected Patterns

- The specification contains an undecidable adjective such as "clear," "concise," or "reasonable" without a test.
- The logical structure is organized by department, source, or file format.
- One object contains several independent lifecycle topics that do not jointly prove one thing.
- "Organization" changes facts, meaning, subjects, limits, or commitments.
- Obsolete content remains in active retrieval.
- An object without a source reference or readable content counts as written.
- An object without validated reuse participates in cross-task decisions as validated knowledge.
- Content is stored without feedback review.
- A strategy is enforced as an invariant despite a justified carrier or domain difference.

# 知识库共同底层框架

## 第一性原理

知识库首先要形成一个人和 Agent 共同使用的知识对象：

> **它能被同时观测、操作、修正和演化，知识在真实使用中持续积累。**

因此，知识库不是只负责存储文件，也不是只负责把答案查得更快。检索只是使用知识对象的一种方式。

## 当前实现选择

本项目当前用本地 Markdown 文件承载共同知识对象。这样做是为了让同一份内容同时满足人的阅读、判断和维护，以及 Agent 的读取、引用和修改：

```text
一篇 Markdown 知识笔记
  ├── Frontmatter：这篇笔记的属性
  ├── 正文：这件事本身
  ├── Wiki 链接：它与其他知识的关系
  └── 图片/附件引用：证据与补充材料的位置
```

这是一种实现方式，不是知识库的第一性原理。目录、编辑器和检索工具都可以替换，但不能重新分裂成人用一套、Agent 用一套。

## 共同知识对象如何形成

原始文档、对话、代码、决策和其他材料是输入与证据。人和 Agent 对它们进行语义整理、消歧、关系补全和事实核对，把真正需要持续复用的内容编译成可独立阅读的 Markdown 笔记。

```text
原始输入
  ↓
语义整理、关系建立、事实核对
  ↓
共同知识对象
  ↓
被人和 Agent 使用、引用、纠正
  └──────────────→ 持续修正和积累
```

这里的“编译”不是要求建立一套额外平台，而是要求长期知识不能停留在每次查询都要重新解释的原始材料里。编译产物要保留来源、状态和可复核位置，让人和 Agent 面对同一份可维护的语义记忆。

## 一篇知识笔记写什么

### 正文：共同理解的内容

正文写人和 Agent 都需要理解的语义。笔记应当独立可读，不依赖“如上”“见前文”才能成立。重要结论写在正文中，不能只放在属性或索引里。

### Frontmatter：跟随笔记的属性

Frontmatter 描述这篇笔记是什么，以及如何筛选、判断和维护它。常见属性包括：

```yaml
---
tags: [业绩案例]
主体: 某某公司
state: verified
source: inbox/企业材料-最终版2.docx
source_location: page=43; table=项目业绩表
valid_to: 2027-12-31
owner: 市场部
---
```

字段不要求所有场景统一，也不要求每篇笔记一开始就填满。真正影响检索、判断、权限或维护的信息才进入 Frontmatter；无法确认的值保持未知或省略。字段名称可以场景化，但字段必须属于笔记本身。

### Wiki 链接：可观察的知识关系

笔记之间的来源、适用、组成、替代、冲突和相关关系，优先用 Markdown Wiki 链接表达，例如 `[[某项资质]]` 或 `[[2025 项目验收]]`。关系要让人和 Agent 都能看到，不只保存在图数据库、外部台账或向量索引中。

### 图片和附件引用：可回到证据

扫描件、证书、合同、照片、表格和其他附件可以继续使用原始格式。Markdown 笔记通过链接或附件索引指出它们在哪里、对应正文哪一条结论。图片是证据，不会因为被链接就自动变成已确认事实，事实状态仍由笔记属性和核对记录说明。

## 原始材料与业务处理

企业交来的 Word、PDF、Excel、图片和聊天记录可以很乱。先保留原件，再进行盘点、摘录、候选笔记和核对。业务流程可以有这些中间结果，便于回溯和恢复；架构不把它们设计成与共同知识对象并列的长期真相层。

长期可复用的结论必须回到共同知识对象中，并带上来源和可复核定位。原始文件是证据，候选和草稿是工作现场，确认后的 Markdown 笔记是人和 Agent 共同使用的语义记忆。

## 知识、规则和任务不能混写

| 内容 | 回答的问题 | 应该放在哪里 |
|---|---|---|
| 知识笔记属性 | 这篇笔记是什么、何时可用 | 该笔记自己的 Frontmatter |
| 知识事实和解释 | 这件事本身是什么 | 该笔记的 Markdown 正文 |
| 知识之间的关系 | 它与哪些知识有关 | Markdown Wiki 链接 |
| 来源证据 | 结论从哪里来 | Markdown 链接、附件引用和 Frontmatter 来源属性 |
| 工作规则 | Agent 应该如何做、何时停 | Skill 或用户确认的长期规则 |
| 当前任务变量 | 这次客户、金额、工期和输出是什么 | 当前任务工作区 |
| 检索辅助 | 怎样更快找到上面的内容 | 可重建的全文、属性、向量和 RAG 层 |

把工作规则写进每篇笔记会让事实和方法混在一起；把笔记属性放到外部台账会让笔记离开台账后失去身份；把当前任务写回长期知识会污染后续工作。

## 状态是业务属性，不是另一套架构

`unknown`、`candidate`、`needs-review`、`verified`、`superseded` 和 `archived` 等状态可以帮助业务回溯，但它们是笔记或处理记录的属性，不是需要单独建设的对象体系。具体状态名由场景决定，原则不变：

- 未确认不能当作已确认；
- 已过期或已替代不能继续作为当前依据；
- 冲突要保留两边来源，直到有人确认；
- 处理失败不能丢失原始材料。

## 检索如何逐步增加

按真实查询问题增加能力：

1. 目录、标题和 Wiki 链接；
2. 全文搜索；
3. Frontmatter 属性过滤；
4. 关键词与语义混合检索；
5. 向量检索；
6. RAG，即先检索共同知识对象和来源，再让模型基于检索结果回答。

向量知识库是索引实现，不是知识库的事实层。RAG 是一次工作过程，不是一个新的知识对象。无论它们是否存在，人都应该可以直接打开 Markdown 笔记和原始证据。

## 场景差异

| 场景 | 共同对象 | 场景额外决定 |
|---|---|---|
| 个人知识库 | 人和 Agent 共同维护的知识对象 | 隐私、阅读路径、个人标签和维护频率 |
| 企业知识库 | 同上 | 多人权限、责任、有效期、正式凭证和确认人 |
| 项目工作区 | 同上，但内容只对当前任务有效 | 客户、金额、工期、保密边界和交付格式 |

企业知识可以被项目引用，项目变量不能自动写回企业知识。个人知识库也遵守同一条边界，只是权限和确认方式更轻。

## 共同验收

- 人和 Agent 使用的是同一个知识对象；
- 一篇笔记离开索引和聊天上下文仍然能读懂；
- 属性跟随笔记保存在 Frontmatter；
- 关系和证据位置对人和 Agent 可见；
- 重要结论能回到原始来源；
- 当前任务不会污染长期知识；
- 删除全文索引、向量索引或 RAG 后，共同知识对象仍然可读、可查和可维护；
- 不确定、冲突或过期内容会明确暴露，而不是被补成确定答案。

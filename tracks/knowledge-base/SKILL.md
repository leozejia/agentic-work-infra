# 知识库 Skill

版本：1.0

## 这个Skill做什么

教AI三件事：
1. **建库**：从零搭建一个知识库的目录结构
2. **用库**：从知识库里找内容，用于具体任务
3. **整理库**：定期检查、补充、淘汰过期内容

## 核心原则

### 人和AI是同一个读者

不做两套结构。写成人看得懂的，AI才读得准。

### 五个目录，各有用途

```
knowledge-base/
├── README.md         # 这个库是什么、怎么用、最后更新时间
├── inbox/            # 待整理的原始材料
├── notes/            # 已整理的知识（按业务场景分类）
├── sources/          # 完整来源文档（只读参考）
└── archive/          # 已失效的内容
```

### 按业务场景分类，不按文档类型

错误：`notes/Word文档/`、`notes/PDF/`、`notes/人力资源部/`

正确：`notes/企业资质/`、`notes/技术能力/`、`notes/业绩案例/`

因为使用时是按任务找（比如"凑标书"），不是按格式或部门找。

### 四条铁律

1. **搜得到**：文件名和目录名用明确的业务术语，不用代号
2. **打开能看懂**：每个文件开头说明"这是什么、从哪来、什么时候的"
3. **同一个问题只有一份答案**：去重，保留最新最准确的版本
4. **失效的移出检索范围**：失效的内容移到archive/，不要混在notes/里

## 场景A：建知识库

用户说"帮我建个知识库"、"搭个知识库"时。

### 步骤

1. **问清楚用途**
   - 这个库是给什么业务用的？（投标？客服？产品文档？）
   - 现在有哪些材料？（零散文件？还是已有文件夹？）

2. **创建五个目录**
   ```bash
   mkdir -p knowledge-base/{inbox,notes,sources,archive}
   ```

3. **写README.md**
   包含四部分：
   - 用途：这个库服务什么业务
   - 目录说明：五个目录各放什么
   - 更新记录：最后整理时间
   - 未命中记录：用户查过但没找到的问题（持续改进的信号）

4. **根据业务设计notes/的子目录**
   
   示例（投标业务）：
   ```
   notes/
   ├── 企业资质/
   ├── 技术能力/
   ├── 业绩案例/
   └── 人员证书/
   ```

5. **把现有材料放到inbox/**
   - 如果用户已有文件，先全部放inbox/
   - 告诉用户：inbox是临时区，后续会整理到notes/

6. **交付检查清单**
   - 五个目录都建了
   - README写清楚了
   - notes/的子目录符合业务场景（不是文档类型）

## 场景B：从知识库检索内容

用户说"从知识库找XX"、"看看知识库里有没有YY"时。

### 步骤

1. **先读README.md**
   - 确认这个库是做什么的
   - 看notes/下有哪些子目录

2. **定位目标目录**
   - 用户要找"企业资质"→ 去notes/企业资质/
   - 用户要找"过往案例"→ 去notes/业绩案例/
   - 如果目录名不清楚，先列出notes/下所有子目录让用户选

3. **读取文件内容**
   - 不要只看文件名，要打开文件读具体内容
   - 如果一个目录下文件很多，先问用户要哪个时间段或哪个类型

4. **返回内容 + 来源**
   格式：
   ```
   [内容摘要]
   
   来源：knowledge-base/notes/企业资质/ISO9001认证.md
   更新时间：2026-03-15
   ```

5. **记录未命中**
   如果找不到，告诉用户：
   - 在notes/XX目录下没找到
   - 要不要去inbox/看看（可能还没整理）
   - 要不要去sources/看原始文档
   
   然后**记录到README.md的"未命中记录"区**：
   ```
   ## 未命中记录
   - 2026-09-18：查询"某某产品报价"，notes/中没有
   ```

## 场景C：整理知识库

用户说"整理一下知识库"、"知识库太乱了"、或定期维护时。

### 步骤

1. **检查inbox/**
   - 有新材料吗？
   - 能提取成notes/里的知识条目吗？
   - 提取后，原文件移到sources/

2. **检查notes/**
   每个文件检查四项：
   - **来源清楚吗**？（从哪来的、什么时候的）
   - **还有效吗**？（过期的、被新版本替代的）
   - **文件名准确吗**？（能一眼看出是什么内容）
   - **有没有重复**？（同一件事是否有多个文件，保留最新最准确的）

3. **移动失效内容**
   - 过期的、被替代的 → 移到archive/
   - 在archive/里按时间或原因分子目录
     ```
     archive/
     ├── 2025年/
     └── 已被替代/
     ```

4. **检查notes/目录结构**
   - 子目录是否还符合当前业务？
   - 某个目录太大了要不要拆分？
   - 某个目录太小了要不要合并？

5. **更新README.md**
   - 记录最后整理时间
   - 如果调整了目录结构，更新说明

6. **交付整理报告**
   ```
   本次整理：
   - 从inbox整理了X个文件到notes
   - 淘汰了Y个过期内容到archive
   - 调整了Z个目录
   ```

## 停止规则

遇到这些情况，停下来问用户：

1. **业务边界不清楚**
   - "这个库到底是给投标用还是客服用？"
   - "XX和YY是同一个业务场景吗？"

2. **内容有效性无法判断**
   - "这份2023年的资质证书还有效吗？"
   - "这两份内容哪个是最新版？"

3. **目录结构需要大调整**
   - "notes/下现在有20个子目录，要不要合并？"
   - "是否要按产品线重新分类？"

## 检查清单

每次执行完，对照这个清单：

- [ ] 五个目录都存在（README、inbox、notes、sources、archive）
- [ ] README.md写清楚了用途、更新时间、未命中记录区
- [ ] notes/的子目录是业务场景，不是文档类型
- [ ] 每个notes/下的文件都标明了来源和时间
- [ ] notes/里没有重复文件（同一件事只有一份最新版本）
- [ ] inbox/里没有积压太多未整理的内容
- [ ] archive/里的内容确实已失效

企业内部培训

Skill：给AI的业务操作手册

Agent工具会变化，Skill可以成为企业长期积累的业务资产。

适用：需要定制AI工作方式的业务场景 读者：AI协调员、业务骨干

01Skill是什么

它是给AI使用的、可复用的业务指令与资源包。

Skill是给AI的业务操作手册。它规定了AI在特定场景下应该遵循什么规则、按什么步骤工作、如何检查结果、遇到异常怎么处理。它仍然以指令为核心，只是被封装成了可发现、可复用、可迭代的工作包。

举例：知识库Skill教AI怎样处理企业资料，

  • 原始文件怎样接收（保持原样，不覆盖旧文件）
  • 怎样生成候选笔记（候选结果不能伪装成正式知识）
  • 怎样记录来源（统一根目录路径，写明页码、表格或消息时间）
  • 什么内容可以正式使用（已确认、未过期、时效明确）
  • 遇到冲突怎么办（保留现场，标记待确认，不自己猜）

为什么不是"提示词"

Skill可以包含提示词式的指令，但它不只是一段临时文本。

Skill是结构化的目录。它的主体是一份AI操作手册：

  • 元数据：这个Skill适用于什么任务
  • 核心流程：应该按什么步骤干活

需要时，还可以挂上参考文档、确定性脚本等素材（第03节讲）。一次性提示可以复用，Skill的优势在于它有目录、边界、版本和验证入口。

02为什么需要Skill

通用AI未必知道你的业务规则，每次从头解释会增加遗漏和漂移。

没有Skill时

每次让AI干活，你都要重新解释业务规则：

  • "原始文件不要覆盖，也不要直接改写"
  • "先生成候选笔记，不要直接写成正式知识"
  • "来源要能定位到具体页码、表格或消息时间"
  • "已经过期的verified内容也不能继续使用"
  • "如果两份资料说的不一样，先标记待确认"

每次重新说明都会增加遗漏和漂移。

有Skill后

你可以说："整理inbox，先给我候选结果。"

支持该规范的客户端可以发现并加载知识库Skill，再按既定规则执行：

  • 原始文件是否安全保留 ✓
  • 候选和正式知识是否分开 ✓
  • 来源路径和原文位置是否清楚 ✓
  • 状态和有效期是否允许正式使用 ✓
  • 遇到冲突时是否停止并保留现场 ✓

Skill提供一致的参考标准；实际稳定性仍要靠工具、脚本、评测和人工责任边界保证。

Skill把重复说明沉淀成可以版本化、检查和持续修正的业务规则。

03一个Skill长什么样

Skill是一个目录。必需的只有 SKILL.md，其余按需才建。

组成

skill-name/ # Skill名称 ├── SKILL.md # 必需：入口，元数据 + 核心流程 ├── references/ # 按需：执行中要查的细节 │ ├── 命名规范.md │ └── 检查清单.md ├── scripts/ # 按需：必须精确重复的操作 │ └── 检查文件.py └── assets/ # 按需：要放进产出里的素材 └── 报告模板.md
部分职责什么时候才建
SKILL.md技能包入口，放元数据和核心流程必需
references/执行中按需查阅的细节，让SKILL.md保持精简细节多到塞不下SKILL.md
scripts/确定性操作，保证每次结果一致有必须精确重复的步骤
assets/直接进入产出的素材（模板、图标、字体）产出要带固定素材

别把"按需"读成"都要建"

三个目录是可选项，用不上就不建。一个合格的Skill可以只有SKILL.md，它没有references、没有scripts、也没有assets，照样成立。

反过来说，为了"凑齐结构"建三个空目录，只会让目录变乱。

SKILL.md（入口文件）

这是兼容客户端识别技能包的入口文件。它分两部分：

1. 元数据（顶部）

--- name: knowledge-base description: > 建设和维护以本地原始文件和Markdown笔记为事实基础的企业知识库。 当用户要收集资料、整理知识、查询企业知识或检查知识库状态时使用。 不适用于写文章、做标书、写代码等具体业务任务。 ---

description是关键线索：兼容客户端通常用它判断任务是否相关。必须写清楚：

  • 做什么（整理知识库）
  • 什么时候用（用户要建知识库、整理资料时）
  • 什么时候不用（不适用于写文章、做PPT）

2. 正文（核心流程）

正文只写高层级的流程和规则，不写细节。细节放在references里按需加载。

为什么要分开？

因为上下文窗口有限。如果把所有细节都塞进SKILL.md，执行时会增加阅读成本，也更容易淹没关键约束。

渐进式披露：先读取元数据判断相关性，再加载核心流程，执行中按需读取参考文档。具体读取顺序和自动化程度由客户端实现决定。

04Skill怎么迭代

Skill不是一次性写完的规范，而是从真实任务中提炼、用反例持续修正的操作手册。

从0.1到0.4，迭代了什么

以知识库Skill为例，一组来自真实问题的迭代记录如下。版本号只用来标记先后，没有绝对规范。

版本遇到的问题改进
0.1 自动整理会移动或覆盖原始文件，失败后无法重来 原件只接收、不覆盖，候选结果与原件分开保存
0.2 AI生成的候选内容看起来像正式知识 增加candidate、needs-review和verified等显式状态
0.3 source相对哪个目录解释不清，原文位置也无法复核 统一按知识库根目录记录source，并增加source_location
0.4 已经过期的笔记仍写着verified，被查询当成正式答案 查询同时检查state和valid_to，时效不明时转为needs-review

每次迭代都是因为真实任务暴露了问题，然后修正规则。

错误的迭代方式

  • 没有真实任务，靠想象写规则
  • 一次成功就当成最终版本
  • 出了问题改提示词，不改Skill
  • 不记录反例，下次又犯同样的错误

正确的迭代流程

  1. 真实任务：选一个真实的工作场景（如整理10份投标资料）
  2. 执行：让AI按当前Skill执行
  3. 检查：对照检查清单，看哪些地方不符合标准
  4. 分析：是Skill规则不清楚？还是AI理解错了？还是规则本身有问题？
  5. 修正：更新Skill，记录这次改了什么、为什么改
  6. 验证：用类似的任务再跑一遍，确认问题解决了

Skill是活的，不是死的。每次真实任务都是一次测试，每个反例都是一次改进机会。

05哪些工作适合做成Skill

不是所有工作都适合做成Skill。判断标准有三条。

判断标准说明
重复性 这项工作会反复发生吗？如果只做一次，不值得做成Skill
规则性 这项工作有明确的规则吗？如果每次都不一样，无法固化
可检查 结果能检查对错吗？如果没法检查，就没法迭代改进

适合做成Skill的工作

适合 知识库整理
重复性：每周都要整理新资料
规则性：文件名规则、来源标记规则明确
可检查：搜得到、打开能看懂、有来源

投标响应编制
重复性：每月多个投标任务
规则性：章节结构、内容提取、格式转换有标准
可检查：覆盖所有要求、没有串项目、格式合规
不适合 创意文案写作
重复性：有
规则性：无，每次创意都不同
可检查：难，好坏是主观的

复杂决策
重复性：低
规则性：无，要综合大量不确定因素
可检查：难，只能事后看结果

一句话判断

如果你能对着一个新人说清楚"这项工作应该怎么做、做成什么样才算合格"，那就适合做成Skill。

如果你自己也说不清楚，或者每次做法都不一样，那就不适合。

06企业可以有哪些Skill

Skill不是越多越好，而是要真正有用。

没有一个通用的"企业标准Skill清单"，每个企业的业务不同，该做哪些Skill只能从自己的活里长出来。这里不给清单，给的是找的方法。

你的业务需要什么Skill？

问自己三个问题：

  1. 哪项工作重复性最高、最消耗人力？
  2. 这项工作有没有明确的标准？
  3. 如果AI能按标准做这项工作，能节省多少时间？

怎么判断一个方向值不值得做

拿一个候选工作过第05节的三条标准：重复性、规则性、可检查。三条都过时通常值得优先投入。需要判断的工作也可以由Skill提供资料、流程和检查项，最终决策仍应有明确责任人。

从最痛的点开始

不要一次做十个Skill。先从最痛的一个点开始：

  • 选一项重复性高、规则明确、人工做很累的工作
  • 写出初版Skill（规则不需要完美）
  • 用真实任务测试，记录哪些地方不对
  • 迭代改进，直到选定场景中的结果能够持续通过检查
  • 再开始做第二个Skill

07Skill的价值

Skill可以把反复使用的业务规则和检查方法沉淀下来。

为什么说Skill是长期资产？

对象能不能换说明
Agent工具
（Workbuddy、Claude、ChatGPT）		 有条件地换 模型、价格、隐私、延迟、连接器和生态都会影响选择。能否迁移取决于接口、权限和评测是否可复用
知识库 应长期积累 企业资质、业绩、技术能力是企业独有的，但仍需要权限、版本和来源治理
Skill 应长期积累 业务规则、工作流程和质量标准可以沉淀，但迁移成本取决于工具依赖和客户端支持
Agent工具会变，但知识库和Skill可以成为企业长期积累的两类重要资产。

Skill库 = 企业 AI 工作标准的一部分

随着Skill的积累，企业会形成自己的Skill库：

企业Skill库/ ├── <业务A>/ # 这块业务的规则 ├── <业务B>/ # 另一块业务 ├── <业务C>/ └── ...

可以把它看成企业 AI 工作标准的一部分：

  • 新员工入职，先学Skill库，这是公司的工作标准
  • 支持该规范的客户端按任务发现对应Skill，按同样的标准执行
  • 业务改进，更新Skill，所有人和AI同步更新

从"每个人有自己的做法"到"公司有统一的标准"，Skill让业务标准可以沉淀、复用、迭代。

Skill也需要失败安全

Skill可能读取敏感资料、执行脚本、调用网络或写入业务文件。发布前要检查资源来源、权限范围、外部依赖和敏感数据处理方式。放进scripts/的代码也要测试和审查。

  • 原始资料不得被覆盖或删除
  • 候选结果和中间结果应当保留
  • 重复执行不能不断制造重复文件
  • 只修改明确授权的目录
  • 候选内容不能直接作为正式结果

08好Skill vs 差Skill

差Skill会增加遗漏和漂移，好Skill让执行标准更一致、结果更容易检查。

差Skill的典型特征

反模式1：把SKILL.md写成长篇提示词

有人把大量细节都塞进入口文件，结果AI加载后表现比裸调用还差。

为什么：SKILL.md越长，阅读成本越高，关键约束越容易被淹没。长度只是信号，真正要看的是流程是否清楚、资源是否按需加载。

反模式2：description写成功能介绍而非触发条件

错误写法："这个Skill提供了完整的投标能力，支持多种招标文件格式"

正确写法："当用户要响应招标、生成标书、或提到'投标'时使用"

为什么：兼容客户端需要从描述中判断任务相关性，功能介绍本身不够具体。

反模式3：多个Skill边界重叠

如果两个Skill的description都覆盖同一类任务，客户端可能难以选择，导致行为不稳定。需要明确边界、优先级和人工选择方式。

反模式4：把确定性操作写在正文让AI"看着办"

例如：格式检查、文件解析、数据转换这些必须精确执行的操作，应该用scripts/里的脚本完成，不应该让AI每次"临场发挥"。

对比总结

维度好Skill差Skill
SKILL.md长度核心流程精简，细节按需分层把大量细节全部塞进入口文件
description触发条件+边界功能介绍
确定性操作交给scripts/写在正文让AI"看着办"
领域知识外置到references/内联在SKILL.md
边界明确"不适用于..."声称什么都能做
迭代记录反例，持续改进一次成功就当最终版

09速查

培训结束后，记住这一页就够。

  1. Skill的定义：给AI的可复用业务指令与资源包，规定在特定场景下遵循什么规则、按什么步骤工作。
  2. 为什么需要Skill：把业务规则固化下来，减少每次解释时的遗漏和漂移。
  3. Skill的结构：必需的只有SKILL.md（入口）；references/、scripts/、assets/按需才建，用不上就不建。
  4. 元数据是关键线索：description帮助兼容客户端判断任务相关性，必须写清楚做什么、什么时候用、什么时候不用。
  5. 渐进式披露：先读取元数据，再按需加载核心流程和参考文档，具体行为由客户端实现决定。
  6. Skill怎么迭代：从真实任务中提炼，用反例持续修正。每次迭代记录改了什么、为什么改。
  7. 适合做成Skill的工作：重复性高、规则明确、结果可检查。创意和决策工作也可以用Skill提供约束和资料，但最终判断要有责任人。
  8. 从最痛的点开始：不要一次做十个Skill，先从最痛的一个点开始，迭代成熟后再做下一个。
  9. Skill是企业AI能力的沉淀：知识库和Skill可以长期积累，但可迁移性取决于格式、工具、权限和评测。
  10. 好Skill vs 差Skill：SKILL.md要精炼、description写触发条件、确定性操作用脚本、持续记录反例改进。

下一步

今天讲了Skill是什么、为什么重要、怎么做。

现在你可以开始：

  1. 识别一项重复性高、规则明确的工作
  2. 写出这项工作的标准（怎么做、做成什么样才算合格）
  3. 用真实任务测试，记录哪些地方不符合标准
  4. 迭代改进，形成你的第一个Skill
Skill是活的，不是死的。持续从真实任务中改进，才能真正发挥价值。

知识库方法论

知识库：让人和 Agent 共同理解同一件事

从混乱的 Office 资料，到人和 Agent 都能观察、核对和维护的 Markdown 知识。

适用：个人与企业都适用的做法 企业案例：传统 Office 资料的整理与复用

这份材料的主张

知识库不是给 Agent 找得更快的资料库，而是人和 Agent 共同面对的一份可观察知识。

当前选择用 Markdown 承载这份共同理解。目录、属性、链接、向量检索和 RAG 都围绕它服务，不能替代它。

第一部分问题与命题

00问题不是没有资料，而是资料失去了身份

传统企业长期使用 Office 文件工作，这个现实必须从设计入口开始面对。

企业的正式工作通常离不开 Word、Excel、PDF、扫描件、图片和聊天记录。合同要用 Word，报价要用 Excel，盖章文件要留 PDF，证书和验收材料可能只有扫描件，过程中的判断又散在聊天记录里。

这些格式本身没有错。过去的工作模式是围绕人展开的：合同要人看、要人签、要人打印和交付，盖章文件要留个纸面凭据。Office 这一套格式天生就是照着人怎么工作长出来的，几十年下来也确实好用，而且很多原件本身就是最重要的原始证据。

问题出在时代变了。现在读这些材料的，除了人，还多了 Agent。同一份文件要同时承担版式、交付、证据和长期知识的职责，四件事压在一个文件上。当我们想把其中一条结论反复用于下一次工作时，人和 Agent 都很难只依靠文件本身判断它是什么、是否还有效、能不能用于当前任务。

于是，知识并不是不存在，而是在重复使用时失效：

常见情况具体问题结果
找不到不知道有这份资料，或者知道有但不知道在哪里重新问人、重新整理、重复做一遍
不敢用找到了，但不知道来源、日期、适用范围和当前状态找到也等于没有找到
两个说法不同文件都在描述同一件事，却没有说明谁替代了谁无法判断应该依据哪一份
用了过期的旧文件没有退出当前使用范围，和新文件一起被拿出来错误结论被当成正确结论使用

真正危险的不是资料暂时找不到，而是找到了却不知道它是否还能代表这件事。

过去，老员工可能凭经验看出“这份文件有点旧了”，再去问人确认。这个补救办法慢，但有时还能挡住错误。Agent 能更快读取和复用材料，也会把没有身份、没有来源或已经过期的内容更快地带到更多任务里。AI 没有创造这个问题，只是把原来隐藏在人工经验里的问题放大了。

因此，知识库首先要解决的不是“怎样把所有文件放在一起”，而是让每条可复用知识重新拥有自己的身份：它说什么、从哪里来、适用于什么、现在是什么状态。

01底层命题：人和 Agent 共同面对同一个知识对象

知识库的价值，不只在于能不能搜到，更在于人和 Agent 是否理解的是同一件事。

知识库的通常含义，是把知识积累下来，让它可以被反复使用。这个目标同时适用于个人和企业：个人保存自己的经验、判断和资料，企业保存能力、项目和制度。

本项目在这个共同含义上提出更具体的要求：

人和 Agent 应该通过同一份可观察、可核对、可维护的知识表达，共同理解同一件事。

这不要求人和 Agent 使用同一个界面，也不要求 Agent 只能通过文件系统工作。人可以用 Obsidian（一种看 Markdown 笔记的软件）或其他编辑器，Agent 可以通过 Skill（工作手册）、MCP（连接外部工具的通道）或 API（程序调用接口）。关键是两者最后都要回到同一个知识对象，而不是人维护一套内容、Agent 依赖另一套隐藏索引。

要求验收问题
看得见人和 Agent 能看到正文、属性、关系和来源位置吗？
看得懂笔记离开聊天上下文后，仍然能说明这件事吗？
找得到换一个人或换一个 Agent 来，也能找到同一条吗？
核得上重要结论能回到原始文件和具体位置吗？
维护得动人知道谁可以确认、修改和撤回它吗？

知识、规则、任务和检索不是一回事

内容回答的问题应该放在哪里
共同知识这件事是什么Markdown 笔记
工作规则Agent 应该怎么做、何时停Skill 或用户确认的长期规则
当前任务这一次的客户、金额、工期和交付物是什么当前任务工作区
检索辅助怎样更快找到和使用上面的内容全文、属性、向量和 RAG 层
第二部分共同知识如何表达

02为什么传统 Office 资料需要另一份表达

Office 是为人设计的，版式替人省了力；换成 Agent 读，这层省力就成了障碍。

Word、Excel 和 PDF 可以被程序解析，也可以被 Agent 读取。真正的问题是，它们往往同时包含正文、版式、表格、批注、嵌入对象、签章和交付要求。人能依靠视觉和经验理解其中的层次：加粗的一行是重点，缩进的一段是从属，页边的小字是备注。机器虽然可以抽取文字，却拿不到这套视觉线索，未必能稳定判断哪些是结论、哪些是模板文字、哪些只是排版或历史备注。

换句话说，这些文件把一部分含义藏在了“看起来是什么样”里，而 Agent 不靠看。如果每次使用都从一份几十页甚至几百页的 Office 文件里重新猜一遍，企业的知识就会停留在“原始材料里可能有答案”的状态。我们需要把真正会被反复使用的结论，另外写成一份含义直接落在文字上的表达，人和 Agent 读到的才是同一份东西。

原始 Office、PDF、Excel、图片和聊天记录 # 证据、交付物和输入，可以保持原样 ↓ Markdown 共同知识笔记 # 人和 Agent 共同阅读、核对和维护

为什么当前选择 Markdown

Markdown 不是因为它能自动消除错误，而是因为它把文字结构直接暴露出来：标题就是标题，列表就是列表，链接就是链接，修改可以被人直接看到，也可以被 Git（一种记录文件每次改动的工具）记录。它适合成为当前的人机共同载体。

这不意味着企业要放弃 Office。合同、证书、报价、盖章文件和最终交付仍然使用原来的格式。长期复用的结论写入 Markdown，原始 Office 文件通过来源和位置继续作为证据。

Obsidian（看 Markdown 笔记的软件）只是查看和维护这些 Markdown 文件的一种界面。换成其他编辑器，文件仍然应该能被人和 Agent 继续读取。工具可以替换，共同知识不能重新分裂成两套。

03一篇共同知识笔记由什么组成

知识的基本单位不是一份藏在系统里的索引，也不是一张独立的外部台账，而是一篇可以独立理解和继续维护的笔记。

一篇笔记要说清这件事本身，也要交代清楚它的属性、关系和证据位置。下面是一个 Markdown 文件打开之后的样子。它是示例，不是必须照抄的模板；箭头右边的说明是我们加的，文件本身没有这几行。

--- type: 业绩案例 ← 这是什么 state: needs-review ← 现在什么状态 subject: 某某公司 ← 关于谁 source: ../inbox/企业材料-最终版2.docx ← 从哪份原件来 source_location: page=43; table=项目业绩表 ← 在原件里的第几页、哪张表 valid_to: 2027-12-31 ← 有效期到哪天 --- # 某某项目业绩 ← 正文：这条知识本身 ## 结论 材料显示，某某公司于 2025 年完成某项目。验收材料仍需核对。 ## 相关知识 - [[某某公司]] ← 关系：双括号指向相关的笔记 - [[项目验收]] ## 证据 - [原始材料](../inbox/企业材料-最终版2.docx)，第 43 页 ← 附件引用：指回原件

箭头后面的说明是我们加的，文件本身没有这几行。开头那几行用英文名写，是因为 Agent 靠固定名字读数；人不用记这些名字，看箭头后面的中文就行。

照着文件从上到下的顺序，一篇笔记有四部分：

部分作用
属性开头两条横线之间的那几行（也叫 Frontmatter），记录这条知识自己的状态、主体、来源和有效期
正文人和 Agent 共同理解的结论和解释，离开聊天上下文后仍能读懂
关系正文里的双括号，如 [[某某公司]]，指向与它相关的其他笔记。括号里写的是那篇笔记的文件名，点开就能跳过去
附件引用指回合同、证书、照片、表格或扫描件的实际位置

属性可以一条一条长出来，不必一开始就填满。没有证据的值就空着，用不到的字段可以不要。这份材料要讲的是为什么需要这些信息；至于写哪些、写成什么样，由人和 Agent 一起定。

属性和文末的证据都在指回原件，区别在用途：属性里的来源给检索和核对用，文末的证据给人点开看。两条一致就行。

文件名的位置：在属性之前

属性写在文件里面，人得先打开才看得到。而找一份文件，最先碰到的其实是它的名字。名字起得对，一眼就知道大概是哪一年的、关于谁的、是一份什么东西，不用打开就能排除一大半。

所以名字也按固定顺序回答三件事：时间、主体、事情，例如 2026-电力施工资质证书-市政总承包二级.md（.md 是 Markdown 文件的后缀，第 02 节讲过）。三个不必都有，顺序一致就行。判断标准只有一句：你以后会拿什么词去搜它，就把这些词放进名字里。反过来，新建文档3.docx、扫描件.pdf 这种名字，能打开，但搜不到，等于没放进来。

还有一条：状态不靠名字，靠属性。名字里写“可用”“已作废”，改一次状态就得改一次名，早晚会漏。这也正是状态和有效期放在属性里、不放进文件名的原因。

状态属于笔记，不属于目录

状态会随着时间变：刚捞出来的可能还是未知（unknown），理过一次的是候选（candidate），等人核对的是待核对（needs-review），确认过的是已确认（verified），被新版本取代的是已替代（superseded），退出当前使用的是已归档（archived）。

这几个词是示例，不是全公司必须统一的一套固定清单。真正必须遵守的是：未确认不能当作已确认，冲突不能被悄悄抹平，过期或已替代的内容不能继续作为当前依据。

第三部分知识如何形成

04入口必须接受混乱资料

企业不能先把资料整理好，才允许进入知识库。

甲方交来的材料可能是一份两百页的 Word、几张扫描证书、多个 Excel、图片、聊天记录和“最终版 2”。系统不能把“已经整理好的 Markdown”当作入口，否则最难的工作会被排除在设计之外。

稳妥的业务过程可以是：

  1. 保留原件原始文件原样保存，不覆盖、不删除、不因为解析失败而丢失。
  2. 盘点内容说明看到了哪些章节、表格、主题、重复项、冲突和缺失。
  3. 形成候选把可能长期复用的片段写成候选笔记，保留页码、章节、表格或消息时间。
  4. 人工核对核对事实、来源、适用范围、有效期、权限和是否允许复用。
  5. 形成正式知识确认后的内容回到共同知识笔记，未知和冲突仍然显式保留。

这几步里的活大部分由 Agent 干，人只需要在两个地方出手：定什么算可复用，以及核对哪一条可以确认。过程要能被看懂，是因为人要能判断 Agent 有没有做对，不是要人自己从头做一遍。

候选、草稿和中间结果可以保留下来备查。这是过程中的中间状态，不是在旁边另建一本长期账。主线只有一条：原始资料经过整理和核对，形成共同知识对象。

关于 inbox、notes、archive

企业可以把 inbox/、notes/、archive/ 作为一种起步约定。这三个英文名对应收件箱、笔记、归档：原始输入放入收件箱，正式知识集中浏览，退场内容保留在归档区。

这不是知识库的成立条件。候选笔记也可以保存在收件区，正式笔记的状态仍然必须写在自己的属性里。目录帮助人浏览，属性才表达这篇笔记当前是什么。

05长期知识、工作规则和当前任务要分开

同一份工作里会出现三种不同性质的内容，混写会让知识库越来越不可靠。

第 01 节讲共同知识时，已经把这三种内容并排列出过一次。这里把它们的边界写清楚：

内容例子边界
长期知识企业资质、已完成项目、技术能力、个人长期经验需要来源、状态和适用范围，供多个任务复用
工作规则响应某类项目时先检查什么、遇到什么情况必须停说明应该如何工作，不伪装成企业事实
当前任务本次客户、金额、工期、临时承诺、草稿和交付文件只对当前任务有效，不能自动反写长期知识

企业知识可以被项目引用。项目变量不能因为被 Agent 用过一次，就自动成为企业知识。个人知识库也遵守同一条边界，只是确认人和权限更简单。

目录可以按浏览习惯、责任、权限、来源或取用方式设计；没有一种目录能同时表达所有维度。跨目录的关系用双括号链接，筛选条件用属性，原始来源用附件引用。不要让目录承担它无法稳定承担的全部含义。

第四部分知识如何被找到

06怎么把一条知识找出来

靠的不是另建一张总表，而是每条笔记自己写得能被找到。

先看一个真问题：“我们以前做过变电站的项目吗？”

Agent 拿到这个问题，会两条路一起找：

找法怎么找用上面的问题举例
按词找拿问题里的词去搜文件名和全文搜“变电站”，命中名字里和正文里提到它的那几条
按意思找用词不一样但意思接近的，也能带出来搜“变电站”，连写“变电所”“升压站”的那几条也能带出来

这两条路都是 Agent 自带的本事，人不需要装什么，也不需要另外维护一张索引表。要让它们管用，条件只有一个：笔记本身写得能被找到。文件名带上关键词（第 03 节讲过），正文把事情说清，属性标上状态和来源。

按词找和按意思找，各管什么

按词找快而且准，认证书编号、合同号、型号这种要一字不差的东西。缺点是换个说法就找不到。

按意思找（也叫语义检索、向量检索）补的正是这一点。它把文字转换成便于比较的表示，找的是意思接近，代价是不够精确，所以它负责把范围扩大，最后还得人看一眼。这两种合起来用，就是现在常说的 RAG：先检索出相关内容，再让模型基于这些内容回答。

它们都是可以删掉、重建的辅助，不是知识本身。索引丢了，笔记还在，重建一次就行。

该下功夫的是把知识写清楚，不是把检索搞复杂。知识写清楚了，普通检索就能找到；知识本身乱，再先进的检索也找不准。

07怎么知道这份知识库靠不靠得住

文件整齐说明不了什么，拿一件真事走一遍才算数。

整齐好办，可靠不好装。判断的办法很简单：随便挑一件真事，看能不能顺着库里的东西办完。下面这几个动作，任何一个做不下去，就说明有个地方没写清。

做这个动作做不下去说明什么
只打开这一篇笔记，把事情讲给同事听笔记没写清，还得靠你脑子里的上下文补
顺着笔记里的来源，翻到原件那一页对上来源没标，或者标错了位置
问一句“这条现在还算数吗”，能当场答上状态没写，或者没人说得清谁确认过
同一件事只找到一份说法旧的没退出，或者冲突没标出来
换个人来，同样能找到并看懂知识只在你脑子里，没落到库里

还有一件事要看：出错的时候能不能收拾。原始文件还在不在，做错的痕迹能不能看见，人能不能直接打开文件改回来。这些比检索快不快更要紧，因为检索可以重建，丢掉的原件找不回来。

不知道比错误的确定更安全。没写的东西标成“不知道”，比随手填一个看着对的答案要好。

第五部分落到企业场景

08企业可以从一批真实 Office 资料开始

企业场景不需要先搭一个复杂平台，也不需要先把历史资料全部整理完。

可以先挑一批真实材料，例如一份综合 Word、几份证书和一个已经完成的项目。原始材料保持原样，Agent 先盘点内容并标出可能复用的片段。人确认其中一条事实后，再把它写成一篇 Markdown 笔记。

知识库里具体放什么？一个文件夹放一个业务上能单独成立的东西，我们叫它知识单元。判断标准很简单：把这一份拿出来，能不能不翻别的资料就用在下一份标书里。能，它就是一个完整的知识单元，单独存一份；不能，说明它只是一段素材，还要和别的东西合起来。

这里有两层：上面是企业自己的知识库，长期用；下面是当前项目的工作区，做完就收。项目里的客户、金额、工期属于这一次的工作，不因为做过一遍就自动变成公司知识。企业知识可以被项目引用，反过来不行。

注意 notes/ 下面没有再按 inbox 那种阶段分，而是按业务分类：资质归资质、业绩归业绩。因为找东西的时候，人想的是“我要一份资质”，不会想“我要一份已经确认过的东西”。

一份就是一件事：一张证、一个业绩、一套方案、一张人员证书。正文写结论，属性写状态和有效期，关系指出它和谁有关，证据指回原件。下次凑标书要用这张证，打开这一份就够了。

这套目录和字段是示例，帮助团队起步，不必成为唯一设计。真正重要的是：笔记自身能说明自己是什么，项目工作区和长期知识有边界，原始 Office 文件能够被核对，自动整理失败不会造成不可恢复的损失。

09容易走偏的地方

这些做法会把一个场景里的经验，误当成所有场景都该照做的规矩。

容易走偏的做法问题在哪里
把 Markdown 当成自动正确的格式Markdown 只是共同表达载体，来源、状态和人工核对仍然必须存在
把目录位置当成状态目录可能帮助浏览，但状态必须跟着笔记写在属性里
另建一张总表登记每条知识总表容易和笔记对不上，改了一边忘了另一边；先让笔记自身写清楚
一开始就上向量数据库或 RAG先把笔记写清楚，多数问题普通搜索就能解决；检索补不了混乱和缺来源
假设 Agent 会自己判断新旧和权威性来源、状态、有效期和使用边界必须被明确表达并逐项检查
把当前项目变量写回长期知识客户、金额、工期和临时承诺会污染后续任务
为了“通顺”改写原始证据正式知识可以提炼，但必须保留原始文件和可复核位置
文件名不带关键词写成 新建文档3.docx、扫描件.pdf，搜的时候搜不到，等于没放进来

定期检查时，不要只看文件是否整齐。拿一个真实的问题试一次：人能不能找到，Agent 能不能找到，两边读到的是不是同一条结论，来源能不能对上原件，过期和冲突有没有写出来。

10速查

如果只记一页，记住下面这些话。

  1. 知识库的核心：让人和 Agent 通过同一份可观察知识，共同理解同一件事。
  2. 传统 Office 该干什么：继续承担编辑、审批、签署、证据和交付；长期复用的结论另写成 Markdown。
  3. Markdown 的位置：当前的人和 Agent 共同载体，不是自动正确的魔法，也不是隐藏数据库的替身。
  4. 一篇笔记的组成：正文、属性、关系、附件引用。
  5. 文件名的顺序：时间、主体、事情，顺序固定，写的是你以后要搜的词；状态和有效期不写名字，写属性。
  6. 属性的原则：属性是可选的，用一条加一条，未知值不要猜；先写正文，属性随后补。
  7. 资料整理的入口：原始资料可以很乱；先保留，再盘点、形成候选、核对，最后形成正式知识。
  8. 主线只有一条：业务可以保留候选和中间结果，长期事实仍然只回到共同知识对象。
  9. 知识和任务的边界：企业事实可以被项目引用，项目变量不能自动写回企业知识。
  10. 怎么被找到：Agent 按词找加按意思找，两条路一起用；人只要把笔记写清楚，不必另建索引表。
  11. 可靠的标准：拿一件真事走一遍，看能不能讲清、能不能回到原件、说不说得清还算不算数、换个人是不是也找得到。

第一步做什么

挑一批真实的 Office 材料，原样保留。让 Agent 先做内容盘点，再选一条真正会被反复使用的结论，写成一篇 Markdown 知识笔记。人核对正文、属性、关系和证据位置，然后用一个真实问题测试它。

先验证共同理解是否成立，再决定是否需要更多目录、字段或检索技术。

本材料讲的是共同方法，不是一套固定规范。目录、字段和步骤都只是示例，具体怎么做按各自场景定。看这份材料的人只需要理解为什么这么做，动手的部分交给 Agent。

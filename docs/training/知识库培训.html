知识库方法论

知识库：让人和 Agent 共同理解同一件事

从混乱的 Office 资料，到人和 Agent 都能观察、核对和维护的 Markdown 知识。

适用：个人与企业都适用的做法 企业案例：传统 Office 资料的整理与复用

这份材料的主张

知识库不是给 Agent 找得更快的资料库，而是人和 Agent 共同面对的一份可观察知识。

当前选择用 Markdown 承载这份共同理解。目录、属性、链接、向量检索和 RAG 都围绕它服务，不能替代它。

第一部分问题与命题

00问题不是没有资料，而是资料失去了身份

传统企业长期使用 Office 文件工作，这个现实必须从设计入口开始面对。

企业的正式工作通常离不开 Word、Excel、PDF、扫描件、图片和聊天记录。合同要用 Word，报价要用 Excel，盖章文件要留 PDF，证书和验收材料可能只有扫描件，过程中的判断又散在聊天记录里。

这些格式没有错。它们适合编辑、审批、签署、打印和交付，也常常是最重要的原始证据。问题在于：同一份文件同时承担了版式、交付、证据和长期知识的职责。当我们想把其中一条结论反复用于下一次工作时，人和 Agent 都很难只依靠文件本身判断它是什么、是否还有效、能不能用于当前任务。

于是，知识并不是不存在，而是在重复使用时失效：

常见情况具体问题结果
找不到不知道有这份资料，或者知道有但不知道在哪里重新问人、重新整理、重复做一遍
不敢用找到了，但不知道来源、日期、适用范围和当前状态找到也等于没有找到
两个说法不同文件都在描述同一件事，却没有说明谁替代了谁无法判断应该依据哪一份
用了过期的旧文件没有退出当前使用范围，和新文件一起被拿出来错误结论被当成正确结论使用

真正危险的不是资料暂时找不到，而是找到了却不知道它是否还能代表这件事。

过去，老员工可能凭经验看出“这份文件有点旧了”，再去问人确认。这个补救办法慢，但有时还能挡住错误。Agent 能更快读取和复用材料，也会把没有身份、没有来源或已经过期的内容更快地带到更多任务里。AI 没有创造这个问题，只是把原来隐藏在人工经验里的问题放大了。

因此，知识库首先要解决的不是“怎样把所有文件放在一起”，而是让每条可复用知识重新拥有自己的身份：它说什么、从哪里来、适用于什么、现在是什么状态。

01底层命题：人和 Agent 共同面对同一个知识对象

知识库的价值，不只在于能不能搜到，更在于人和 Agent 是否理解的是同一件事。

知识库的通常含义，是把知识积累下来，让它可以被反复使用。这个目标同时适用于个人和企业：个人保存自己的经验、判断和资料，企业保存能力、项目和制度。

本项目在这个共同含义上提出更具体的要求：

人和 Agent 应该通过同一份可观察、可核对、可维护的知识表达，共同理解同一件事。

这不要求人和 Agent 使用同一个界面，也不要求 Agent 只能通过文件系统工作。人可以用 Obsidian（一种看 Markdown 笔记的软件）或其他编辑器，Agent 可以通过 Skill（工作手册）、MCP（连接外部工具的通道）或 API（程序调用接口）。关键是两者最后都要回到同一个知识对象，而不是人维护一套内容、Agent 依赖另一套隐藏索引。

要求验收问题
看得见人和 Agent 能看到正文、属性、关系和来源位置吗？
看得懂笔记离开聊天上下文后，仍然能说明这件事吗？
找得到能从根目录、标题、全文、属性和链接逐步找到它吗？
核得上重要结论能回到原始文件和具体位置吗？
维护得动人知道谁可以确认、修改和撤回它吗？

知识、规则、任务和检索不是一回事

内容回答的问题应该放在哪里
共同知识这件事是什么Markdown 笔记
工作规则Agent 应该怎么做、何时停Skill 或用户确认的长期规则

检索辅助怎样更快找到和使用上面的内容全文、属性、向量和 RAG 层
第二部分共同知识如何表达

02为什么传统 Office 资料需要另一份表达

不是因为 Word 不能被机器读取，而是因为它不适合独自承担长期共享的含义。

Word、Excel 和 PDF 可以被程序解析，也可以被 Agent 读取。真正的问题是，它们往往同时包含正文、版式、表格、批注、嵌入对象、签章和交付要求。人能依靠视觉和经验理解其中的层次，机器虽然可以抽取文字，却未必能稳定判断哪些是结论、哪些是模板文字、哪些只是排版或历史备注。

如果每次使用都从一份几十页甚至几百页的 Office 文件里重新猜一遍，企业的知识就会停留在“原始材料里可能有答案”的状态。我们需要把真正会被反复使用的结论，另外写成一份更容易共同阅读、修改、引用和核对的表达。

原始 Office、PDF、Excel、图片和聊天记录 # 证据、交付物和输入，可以保持原样 ↓ Markdown 共同知识笔记 # 人和 Agent 共同阅读、核对和维护

为什么当前选择 Markdown

Markdown 不是因为它能自动消除错误，而是因为它把文字结构直接暴露出来：标题就是标题，列表就是列表，链接就是链接，修改可以被人直接看到，也可以被 Git（一种记录文件每次改动的工具）记录。它适合成为当前的人机共同载体。

这不意味着企业要放弃 Office。合同、证书、报价、盖章文件和最终交付仍然使用原来的格式。长期复用的结论写入 Markdown，原始 Office 文件通过来源和位置继续作为证据。

Obsidian（看 Markdown 笔记的软件）只是查看和维护这些 Markdown 文件的一种界面。换成其他编辑器，文件仍然应该能被人和 Agent 继续读取。工具可以替换，共同知识不能重新分裂成两套。

03一篇共同知识笔记由什么组成

知识的基本单位不是一份藏在系统里的索引，也不是一张独立的外部台账，而是一篇可以独立理解和继续维护的笔记。

一篇笔记要把这件事本身说清楚，同时把判断它所需要的属性、关系和证据位置暴露出来。打开一个 Markdown 文件，看到的就是下面这样：

--- ← 文件开头的一段属性，习惯上叫 Frontmatter type: 业绩案例 ← 这是什么 state: needs-review ← 待核对 subject: 某某公司 ← 关于谁 source: ../inbox/企业材料-最终版2.docx ← 从哪份原文件来 source_location: page=43; table=项目业绩表 ← 在原文件的第几页、哪张表 valid_to: 2027-12-31 ← 有效期到哪天 --- ← 属性到这里结束，下面是正文 # 某某项目业绩 ## 结论 材料显示，某某公司于 2025 年完成某项目。验收材料仍需核对。 ## 相关知识 - [[某某公司]] - [[项目验收]] ## 证据 - [原始材料](../inbox/企业材料-最终版2.docx)，第 43 页，项目业绩表

上面的名字是固定的，含义也不难：type 是类型，state 是状态，subject 是主体，source 是来源，source_location 是来源里的具体位置，valid_to 是有效期到哪天。机器靠这些固定名字读数，人靠名字后面的中文理解意思。

按作用分，一篇笔记有四部分：

部分作用
正文写人和 Agent 共同理解的结论和解释，笔记离开聊天上下文后仍能读懂
属性（Frontmatter）写在文件开头的一段固定名字的值，如状态、主体、来源、有效期、负责人和标签
关系（Wiki 链接）写在正文里的双方括号，如 [[某某公司]]，表示这条知识与哪几条相关
附件引用指回合同、证书、照片、表格或扫描件的实际位置和对应内容

属性和证据都在指回原始文件，区别在于用途：属性里的 source 和 source_location 是给检索和核对用的，指明这条知识从哪一页来；正文末尾的「证据」是给人看的，方便顺着点开原件。两条都写不算重复，一致就行。

属性不要求一开始填满。只有真正影响检索、判断、权限或维护的信息才值得写入；没有证据的值保持未知或省略。证据也不需要全部复制进笔记，笔记只需要让人和 Agent 能回到它。

文件名的位置：在属性之前

属性写在文件里面，人得先打开才看得到。而找到一份文件，最先碰到的其实是它的名字。名字起得对，一眼就知道大概是哪一年的、关于谁的、是一份什么东西，不用打开就能排除一大半。

所以一个能用的名字，也按固定顺序回答三件事：先说时间（年份或日期），再说主体（客户、项目、产品、型号），最后说这是什么事（资质证书、投标报价、技术方案、验收记录）。

三个不必每个都出现。公司自己的资质证书，主体就是本公司，不用写进名字。缺哪个不影响，要紧的是写进去的那几个顺序保持一致，电脑排起来才整齐。套进去就是：2026-电力施工资质证书-市政总承包二级.md、2025-某某变电站项目-投标报价.md。

判断标准只有一句：你以后会拿什么词去搜它，就把这些词放进名字里。而 新建文档3.docx、扫描件.pdf 这种名字，能打开，但你永远想不起来里面是什么，也搜不到。

有一条最容易被违反：状态不靠名字，靠属性。名字里写“可用”“已作废”，改一次状态就得改一次名，早晚会漏。状态和有效期都放在属性里，名字只负责让人认出来这是什么。

状态属于笔记，不属于目录

状态会随着时间变：刚捞出来的可能还是未知（unknown），理过一次的是候选（candidate），等人核对的是待核对（needs-review），确认过的是已确认（verified），被新版本取代的是已替代（superseded），退出当前使用的是已归档（archived）。

这几个词是示例，不是全公司必须统一的一套固定清单。真正必须遵守的是：未确认不能当作已确认，冲突不能被悄悄抹平，过期或已替代的内容不能继续作为当前依据。

第三部分知识如何形成

04入口必须接受混乱资料

企业不能先把资料整理好，才允许进入知识库。

甲方交来的材料可能是一份两百页的 Word、几张扫描证书、多个 Excel、图片、聊天记录和“最终版 2”。系统不能把“已经整理好的 Markdown”当作入口，否则最难的工作会被排除在设计之外。

稳妥的业务过程可以是：

  1. 保留原件原始文件原样保存，不覆盖、不删除、不因为解析失败而丢失。
  2. 盘点内容说明看到了哪些章节、表格、主题、重复项、冲突和缺失。
  3. 形成候选把可能长期复用的片段写成候选笔记，保留页码、章节、表格或消息时间。
  4. 人工核对核对事实、来源、适用范围、有效期、权限和是否允许复用。
  5. 形成正式知识确认后的内容回到共同知识笔记，未知和冲突仍然显式保留。

候选、草稿和中间结果可以为了回溯和恢复而保留。这是业务过程上的中间状态，不是在旁边另建一本长期账。主线只有一条：原始资料经过整理和核对，形成共同知识对象。

关于 inbox、notes、archive

企业可以把 inbox/、notes/、archive/ 作为一种起步约定。这三个英文名对应收件箱、笔记、归档：原始输入放入收件箱，正式知识集中浏览，退场内容保留在归档区。

这不是知识库的成立条件。候选笔记也可以保存在收件区，正式笔记的状态仍然必须写在自己的属性里。目录帮助人浏览，属性才表达这篇笔记当前是什么。

05长期知识、工作规则和当前任务要分开

同一份工作里会出现三种不同性质的内容，混写会让知识库越来越不可靠。

第 01 节讲共同知识时，已经把这三种内容并排列出过一次。这里把它们的边界写清楚：

内容例子边界
长期知识企业资质、已完成项目、技术能力、个人长期经验需要来源、状态和适用范围，供多个任务复用
工作规则响应某类项目时先检查什么、遇到什么情况必须停说明应该如何工作，不伪装成企业事实
当前任务本次客户、金额、工期、临时承诺、草稿和交付文件只对当前任务有效，不能自动反写长期知识

企业知识可以被项目引用。项目变量不能因为被 Agent 用过一次，就自动成为企业知识。个人知识库也遵守同一条边界，只是确认人和权限更简单。

目录可以按浏览习惯、责任、权限、来源或取用方式设计；没有一种目录能同时表达所有维度。跨目录的关系用关系链接（[[某某公司]] 这种写法），筛选条件用属性，原始来源用附件引用。不要让目录承担它无法稳定承担的全部含义。

第四部分知识如何被找到

06先让知识可观察，再逐步增加检索

检索是使用共同知识的方式，不是在旁边再建一套知识。

没有知识地图时，Agent 也应该能从知识库根目录开始工作：

  1. 看根目录先看根目录里有哪些 Markdown 文件，从文件名、标题和已有目录圈出一个候选范围。
  2. 搜全文用客户名、证书编号、项目名、技术词和原文句子缩小范围。
  3. 筛属性按属性里的类型、状态、主体、有效期和标签过滤。
  4. 沿链接打开完整笔记，沿关系链接和附件引用继续核对。
  5. 再加语义检索当关键词和目录确实找不到该找的东西时，再增加这个手段。语义检索是不靠同一个词、而靠意思接近来找。

走到第五步之前，前四步都已经能被人独立完成，Agent 只是做得更快。这也是判断检索技术该不该上的标准：前四步够用，就先不上。

向量检索和 RAG 在这里是什么

向量检索是语义检索的一种实现：把文字转换成便于比较的表示，帮助找到用词不同但可能相关的内容。比如你搜“抗震要求”，它能带出写“抗地震设防”的那条。它适合扩大找回的范围，不适合单独判断证书编号、日期和有效性。

RAG是一个工作过程：先检索共同知识和来源，把相关内容交给模型，再让模型基于这些内容生成回答。RAG 不保证检索正确，也不自动保证答案真实。

因此，向量索引和 RAG 都是可删除、可替换、可重建的辅助层。无论它们是否存在，人都应该能直接打开 Markdown 笔记和原始证据。

先建立能被人看懂、能被 Agent 核对的知识，再解决怎样更快找到它。

07可靠性不是“整理完成”，而是能持续被检查

知识库是否好用，要用真实问题验证，而不是只看文件是否整齐。

一份正式知识至少要能回答：

  • 这篇笔记在说什么，单独打开能不能看懂？
  • 它从哪里来，能不能回到原始文件和具体位置？
  • 它当前是什么状态，谁可以确认或修改？
  • 它是否已经被替代、过期或与其他笔记冲突？
  • 当前项目是否只是引用了它，还是误把项目变量写回了它？
  • 删除全文索引、向量索引或 RAG 后，人和 Agent 是否仍能接管？

失败时的最低要求

原始文件仍然存在，候选和失败现场仍然可见，失败步骤和原因可以说明，人可以直接编辑 Markdown、重试或更换工具继续工作。未知比错误的确定更安全。

第五部分落到企业场景

08企业可以从一批真实 Office 资料开始

企业场景不需要先搭一个复杂平台，也不需要先把历史资料全部整理完。

可以先挑一批真实材料，例如一份综合 Word、几份证书和一个已经完成的项目。原始材料保持原样，Agent 先盘点内容并标出可能复用的片段。人确认其中一条事实后，再把它写成一篇有正文、属性、关系和证据引用的 Markdown 笔记。

company-vault/ # 公司的知识库，实际用公司自己的名字 ├── inbox/ # 收件箱：原始材料和候选 ├── notes/ # 笔记：方便浏览的正式知识 └── archive/ # 归档：已替代或退出当前使用范围的内容 work/ └── 2026-某项目/ # 当前客户、金额、工期、草稿和交付物

这里有两层：上面是企业自己的知识库，长期用；下面是当前项目的工作区，做完就收。项目里的客户、金额、工期属于这一次的工作，不因为做过一遍就自动变成公司知识。企业知识可以被项目引用，反过来不行。

这套目录可以帮助团队开始，但不应该成为企业知识库的唯一设计。真正重要的是：笔记自身能说明自己是什么，项目工作区和长期知识有边界，原始 Office 文件能够被核对，自动整理失败不会造成不可恢复的损失。

09容易走偏的地方

这些做法会把一个场景里的经验，误当成所有场景都该照做的规矩。

容易走偏的做法问题在哪里
把 Markdown 当成自动正确的格式Markdown 只是共同表达载体，来源、状态和人工核对仍然必须存在
把目录位置当成状态目录可能帮助浏览，但状态必须跟着笔记写在属性里
先建知识地图、台账或隐藏索引外部登记容易和笔记分叉，先让笔记自身可观察
一开始就上向量数据库或 RAG检索层不能修复混乱、冲突和没有来源的知识
假设 Agent 会自己判断新旧和权威性来源、状态、有效期和使用边界必须被明确表达并逐项检查
把当前项目变量写回长期知识客户、金额、工期和临时承诺会污染后续任务
为了“通顺”改写原始证据正式知识可以提炼，但必须保留原始文件和可复核位置
文件名不带关键词写成 新建文档3.docx、扫描件.pdf，搜的时候搜不到，等于没放进来

定期检查时，不要只看文件是否整齐。拿真实问题试一次：人能否找到，Agent 能否找到，双方是否读到同一条结论，来源能否核对，过期和冲突是否显式，找不到时是否能够报告缺口。

10速查

如果只记一页，记住下面这些话。

  1. 知识库的核心：让人和 Agent 通过同一份可观察知识，共同理解同一件事。
  2. 传统 Office 该干什么：继续承担编辑、审批、签署、证据和交付；长期复用的结论另写成 Markdown。
  3. Markdown 的位置：当前的人和 Agent 共同载体，不是自动正确的魔法，也不是隐藏数据库的替身。
  4. 一篇笔记的组成：正文、属性、关系、附件引用。
  5. 文件名的顺序：时间、主体、事情，顺序固定，写的是你以后要搜的词；状态和有效期不写名字，写属性。
  6. 属性的原则：属性跟随笔记，字段按场景增加，未知值不要猜。
  7. 资料整理的入口：原始资料可以很乱；先保留，再盘点、形成候选、核对，最后形成正式知识。
  8. 主线只有一条：业务可以保留候选和中间结果，长期事实仍然只回到共同知识对象。
  9. 知识和任务的边界：企业事实可以被项目引用，项目变量不能自动写回企业知识。
  10. 检索的顺序：根目录、标题、全文、属性、关系链接，再按真实需要增加语义检索、向量检索和 RAG。
  11. 可靠性的标准：能看懂、找得到、核得上、知道状态、能维护，失败后人还能接手。

第一步做什么

挑一批真实的 Office 材料，原样保留。让 Agent 先做内容盘点，再选一条真正会被反复使用的结论，写成一篇 Markdown 知识笔记。人核对正文、属性、关系和证据位置，然后用一个真实问题测试它。

先验证共同理解是否成立，再决定是否需要更多目录、字段或检索技术。

本材料提出共同底层方法。目录、字段、权限和工作步骤应根据个人或企业场景调整，不要把企业示例直接当成全局协议。

# Skill 设计最佳实践

## Skill 是什么

Skill 是一组可复用的工作规则和资源。它告诉 Agent：

- 什么时候适用；
- 需要哪些输入；
- 应该按什么步骤工作；
- 什么结果才算完成；
- 遇到什么情况必须停下来交给人。

Skill 不是某个知识库的替代品，也不是把一次性提示词换个文件名。知识库保存材料和结论，Skill 规定怎样使用材料完成一类工作。

## 一个 Skill 的组成

一个 Skill 通常是一个目录。必须有 `SKILL.md`，其他目录按需要建立：

```text
skill-name/
├── SKILL.md              # 必需：元数据和核心流程
├── references/           # 可选：执行时需要查阅的细节
├── scripts/              # 可选：必须精确重复的操作
└── assets/               # 可选：要放进产出的固定素材
```

| 部分 | 职责 | 什么时候才建 |
|---|---|---|
| `SKILL.md` | 入口、适用范围、核心流程和停止规则 | 必需 |
| `references/` | 详细规则、示例、领域资料 | 细节已经影响入口文件的可读性 |
| `scripts/` | 解析、转换、检查等确定性操作 | 让 Agent 临场发挥会造成不稳定 |
| `assets/` | 模板、图标、字体等固定素材 | 产出确实需要这些素材 |

这些目录不是评分表。一个只有 `SKILL.md` 的 Skill 可以成立；为了凑结构建立空目录，反而会增加混乱。

## `SKILL.md` 应该写什么

顶部元数据至少要说明：

```yaml
---
name: skill-name
description: >
  做什么。
  什么时候使用。
  不适用于什么。
---
```

`description` 是相关性线索，应该写触发条件和边界，不要只写功能宣传语。正文放高层级流程、输入、输出、检查和停止规则。详细材料按需放到 `references/`，确定性操作交给脚本或正式工具。

客户端是否支持自动发现、分层加载或某些额外字段，要以实际客户端行为为准，不把一种客户端的行为说成所有 Agent 的标准。

## 从真实任务迭代

Skill 应从反复出现的真实工作中长出来：

1. 选一项真实任务；
2. 让 Agent 按当前 Skill 执行；
3. 检查用户真正要的结果；
4. 记录是规则不清、执行错误还是规则本身不对；
5. 只修改能解释这个问题的部分；
6. 用相似任务回归验证。

版本号只用于标记迭代先后，没有统一的绝对格式。重要的是记录改了什么、为什么改，以及哪个反例促成了这次修改。

## 判断一项工作是否值得做成 Skill

先看三件事：

- 是否重复发生；
- 是否有可以说明白的规则；
- 结果是否能检查。

创意和决策工作也可以使用 Skill，但 Skill 应提供资料、流程和检查项，不能伪装成替人承担最终责任的自动决策系统。

## 失败安全

任何会读取、整理或写入材料的 Skill，都应该做到：

- 不覆盖、不删除无法恢复的原始材料；
- 保留候选结果和中间结果；
- 重复执行不会无止境地产生重复结果；
- 失败时报告失败步骤、原因和当前状态；
- 只修改明确授权的范围；
- 不把候选、待确认或过期内容当作正式结果；
- 高级索引、缓存和生成结果可以重建或删除。

## 场景化而不是写死

共同 Skill 规则应只保留跨场景都成立的边界。目录名、字段、权限、审批、格式和领域术语，应写在具体场景 Skill 或参考材料中。

例如：企业投标可能需要项目隔离、证书有效期和交付格式；个人研究可能更关心隐私、阅读路径和个人偏好。它们可以共享“来源清楚、未知不伪装、当前任务不污染长期材料”的底层要求，但不需要共用同一套字段。

## 一句话判断

> 好 Skill 让 Agent 在一类真实工作中更稳定、更容易检查、更容易失败后接管；它不会把一个场景的习惯伪装成所有场景的基础设施。

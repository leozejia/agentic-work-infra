# Skill 设计最佳实践

## Skill 是什么

Skill 是围绕共同知识对象运行的一组可复用工作规则和资源。它告诉 Agent：

- 什么时候适用；
- 需要哪些输入；
- 应该按什么步骤工作；
- 什么结果才算完成；
- 遇到什么情况必须停下来交给人。

Skill 负责回答“这件事应该怎么做”。共同知识对象负责回答“这件事是什么”。二者可以互相引用，但不能互相替代。

## Skill 与共同知识对象的边界

- 知识笔记的正文、Frontmatter、Wiki 链接和附件引用记录事实、属性、关系和证据。
- Skill 记录步骤、检查项、停止条件、权限边界和输出约束。
- 当前任务工作区记录这一次的客户、金额、工期、草稿和交付物。
- 用户确认的长期工作规则属于规则层，场景可以称为 RSI、行为规则或其他名称。

不要把企业事实写进 Skill，也不要把“应该如何工作”塞进每篇知识笔记的 Frontmatter。笔记属性必须留在笔记自己的 Frontmatter 中。

## 一个 Skill 的组成

一个 Skill 通常是一个目录。必须有 `SKILL.md`，其他目录按需要建立：

```text
skill-name/
├── SKILL.md              # 必需：元数据和核心流程
├── references/           # 可选：执行时需要查阅的细节
├── scripts/              # 可选：必须精确重复的操作
└── assets/               # 可选：要放进产出的固定素材
```

一个只有 `SKILL.md` 的 Skill 可以成立。为了凑结构建立空目录，只会增加认知成本。

## `SKILL.md` 应该写什么

顶部元数据至少说明：

```yaml
---
name: skill-name
description: >
  做什么。
  什么时候使用。
  不适用于什么。
---
```

正文放适用范围、核心流程、输入、输出、检查和停止规则。详细材料按需放到 `references/`，确定性操作交给脚本或正式工具。不要把某个客户端的加载行为写成所有 Agent 的标准。

## 从真实任务迭代

Skill 应从反复出现的真实工作中长出来：

1. 选一项真实任务；
2. 让 Agent 按当前 Skill 执行；
3. 检查用户真正需要的结果；
4. 区分规则不清、执行错误和规则本身不对；
5. 只修改能解释这个问题的部分；
6. 用相似任务回归验证。

迭代的是工作规则，不是共同知识对象的底层原则。无论 Skill 怎样改，当前实现中的知识仍然回到 Markdown，属性仍然在笔记自己的 Frontmatter，关系仍然对人和 Agent 可见。

## 失败安全

任何会读取、整理或写入共同知识对象的 Skill，都应该做到：

- 不覆盖、不删除无法恢复的原始材料；
- 保留候选结果和失败现场；
- 重复执行不会无止境地产生重复结果；
- 失败时报告失败步骤、原因和当前状态；
- 只修改明确授权的范围；
- 不把候选、待确认或过期内容当作正式结果；
- 高级索引、缓存和生成结果可以重建或删除。

## 场景化而不是分叉

共同 Skill 只保留跨场景成立的边界和工作循环。场景可以补充目录、字段、权限、审批、业务步骤和领域术语，但不得另建一套与共同知识对象互相竞争的事实架构。

企业投标可以要求证书有效期和项目隔离，个人研究可以更重视隐私和阅读路径。它们共享同一套知识表达基础，只在规则和任务层做差异化。

## 一句话判断

> 好 Skill 让 Agent 在一类真实工作中更稳定、更容易检查、更容易失败后接管；它规定工作方法，不把一个场景的习惯伪装成全局基础设施，也不把事实藏到共同知识对象之外。

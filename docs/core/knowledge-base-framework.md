# 知识库的共同底层框架

## 核心目标

知识库不是为了让 Agent 单独查得更快，也不是把文件换成一个隐藏的数据库。它要提供一块人和 Agent 共同使用的知识表面：

> **人和 Agent 都能看懂、找到、核对、使用和维护同一份知识。**

因此，本项目的共同知识载体固定为 Markdown 文件。Obsidian 是观察、编辑和链接这些文件的一种界面；其他工具可以同步、展示、索引或转换，但不能产生脱离 Markdown 的第二套知识真相。

## 一篇知识笔记的固定组成

```text
一篇 Markdown 知识笔记
  ├── Frontmatter：这篇笔记的属性
  ├── 正文：这件事本身
  ├── Wiki 链接：它与其他知识的关系
  └── 图片/附件引用：证据与补充材料的位置
```

### 正文：共同理解的内容

正文写人和 Agent 都需要理解的语义。笔记应当独立可读，不依赖“如上”“见前文”才能成立。重要结论写在正文中，不能只放在属性或索引里。

### Frontmatter：跟随笔记的属性

Frontmatter 描述这篇笔记是什么，以及如何筛选、判断和维护它。常见属性包括：

```yaml
---
tags: [业绩案例]
主体: 某某公司
state: verified
source: inbox/企业材料-最终版2.docx
source_location: page=43; table=项目业绩表
valid_to: 2027-12-31
owner: 市场部
---
```

字段不要求所有场景统一，也不要求每篇笔记一开始就填满。真正影响检索、判断、权限或维护的信息才进入 Frontmatter；无法确认的值保持未知或省略。**字段的名称可以场景化，字段必须属于笔记本身。**

### Wiki 链接：可观察的知识关系

笔记之间的来源、适用、组成、替代、冲突和相关关系，优先用 Markdown Wiki 链接表达，例如 `[[某项资质]]` 或 `[[2025 项目验收]]`。关系要让人和 Agent 都能看到，不只保存在图数据库、外部台账或向量索引中。

### 图片和附件引用：可回到证据

扫描件、证书、合同、照片、表格和其他附件可以继续使用原始格式。Markdown 笔记通过链接或附件索引指出它们在哪里、对应正文哪一条结论。图片是证据，不会因为被链接就自动变成已确认事实；事实状态仍由笔记属性和核对记录说明。

## 原始材料与业务处理

企业交来的 Word、PDF、Excel、图片和聊天记录可以很乱。系统先保留原件，再进行盘点、摘录、候选笔记和核对。业务流程可以有这些中间结果，便于回溯和恢复；架构不把它们设计成与 Markdown 知识并列的长期真相层。

长期可复用的结论必须回到 Markdown 知识笔记中，并带上来源和可复核定位。原始文件是证据，候选和草稿是工作现场，确认后的 Markdown 笔记是共同理解的可复用表达。

## 知识、规则和任务不能混写

| 内容 | 回答的问题 | 应该放在哪里 |
|---|---|---|
| 知识笔记属性 | 这篇笔记是什么、何时可用 | 该笔记自己的 Frontmatter |
| 知识事实和解释 | 这件事本身是什么 | 该笔记的 Markdown 正文 |
| 知识之间的关系 | 它与哪些知识有关 | Markdown Wiki 链接 |
| 来源证据 | 结论从哪里来 | Markdown 链接、附件引用和 Frontmatter 来源属性 |
| 工作规则 | Agent 应该如何做、何时停 | Skill 或用户确认的长期规则 |
| 当前任务变量 | 这次客户、金额、工期和输出是什么 | 当前任务工作区 |
| 检索辅助 | 怎样更快找到上面的内容 | 可重建的全文、属性、向量和 RAG 层 |

把工作规则写进每篇笔记会让事实和方法混在一起；把笔记属性放到外部台账会让笔记离开台账后失去身份；把当前任务写回长期知识会污染后续工作。

## 状态是业务属性，不是另一套架构

`unknown`、`candidate`、`needs-review`、`verified`、`superseded` 和 `archived` 等状态可以帮助业务回溯，但它们是笔记或处理记录的属性，不是需要单独建设的对象体系。具体状态名由场景决定，原则不变：

- 未确认不能当作已确认；
- 已过期或已替代不能继续作为当前依据；
- 冲突要保留两边来源，直到有人确认；
- 处理失败不能丢失原始材料。

## 检索如何逐步增加

按真实查询问题增加能力：

1. 目录、标题和 Wiki 链接；
2. 全文搜索；
3. Frontmatter 属性过滤；
4. 关键词与语义混合检索；
5. 向量检索；
6. RAG，即先检索 Markdown 知识和来源，再让模型基于检索结果回答。

向量知识库是索引实现，不是知识库的事实层。RAG 是一次工作过程，不是一个新的知识对象。无论它们是否存在，人都应该可以直接打开 Markdown 笔记和原始证据。

## 场景差异

| 场景 | 共同表达 | 场景额外决定 |
|---|---|---|
| 个人知识库 | Markdown、Frontmatter、Wiki、附件引用 | 隐私、阅读路径、个人标签和维护频率 |
| 企业知识库 | 同上 | 多人权限、责任、有效期、正式凭证和确认人 |
| 项目工作区 | 同上，但内容只对当前任务有效 | 客户、金额、工期、保密边界和交付格式 |

企业知识可以被项目引用，项目变量不能自动写回企业知识。个人知识库也要遵守同一条边界，只是权限和确认方式更轻。

## 共同验收

- 人和 Agent 看到的是同一套 Markdown 知识；
- 一篇笔记离开索引和聊天上下文仍然能读懂；
- 属性跟随笔记保存在 Frontmatter；
- 关系和证据位置对人和 Agent 可见；
- 重要结论能回到原始来源；
- 当前任务不会污染长期知识；
- 删除全文索引、向量索引或 RAG 后，核心知识仍然可读、可查和可维护；
- 不确定、冲突或过期内容会明确暴露，而不是被补成确定答案。

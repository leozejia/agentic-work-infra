# 知识库的共同底层框架

## 先区分“共同框架”和“场景实现”

个人知识库、企业知识库和项目知识库的载体、权限、字段和维护人可以不同，但它们都在解决同一类问题：

> **把会被反复使用的材料整理成，人和 Agent 都能找到、理解、核对和继续维护的内容。**

共同框架只规定问题的边界，不规定所有场景必须长成同一棵目录树。

## 知识系统会接触四类内容

知识库相关工作通常会接触四类内容：

1. **来源材料**：原始文件、网页、记录、数据和外部输入。
2. **整理结果**：摘要、拆分片段、索引和候选笔记。
3. **可复用知识**：经过确认、可以在相似任务中引用的内容。
4. **当前使用记录**：这一次任务选择了什么、修改了什么、还缺什么。它通常属于当前任务工作区，只通过引用连接回知识库。

这四类内容可以放在不同目录、不同系统或同一套文件中，关键是它们的身份不能混在一起。

## 一条共同生命周期

```text
进入
  ↓
识别和整理
  ↓
核对
  ↓
复用
  ↓
更新、替代或停止使用
```

每一步都应该能回答：内容从哪里来、现在是什么状态、谁可以使用、下一步由谁确认。

“原始、候选、已确认、已替代”是常见的状态区别，但状态名称可以按场景调整。共同要求是：**没有确认的内容不能伪装成已经确认，已经失效的内容不能继续被当作当前答案。**

## 哪些信息应该变成字段

字段不是越多越好。只有当某个信息会影响查找、判断、权限或维护时，才值得显式记录。

- 轻量个人笔记可能只需要标题和正文。
- 需要复用的结论通常需要来源或出处。
- 影响业务决策的内容通常还需要状态、适用范围和更新时间。
- 多人共用的内容可能需要负责人、权限和确认记录。
- 有明确有效期的内容才需要有效期字段。

不能为了让文件看起来完整，让 Agent 猜字段值。

## 检索是逐步增加的能力

检索能力可以按真实失败逐步增加：

1. 目录、标题和链接；
2. 全文搜索；
3. 必要的属性过滤；
4. 关键词与语义的混合检索；
5. 向量检索；
6. 让模型基于检索结果回答，也就是 RAG。

向量索引是搜索辅助物，RAG 是一次“先找材料、再生成回答”的工作过程。它们都不应成为唯一事实来源，也不应阻止人直接查看和维护原始材料及可复用内容。

## 三类场景的差异

| 场景 | 共同部分 | 需要单独决定的部分 |
|---|---|---|
| 个人知识库 | 来源、整理、复用、检索、更新 | 隐私、个人偏好、维护成本 |
| 企业知识库 | 来源、状态、适用范围、复用、核对 | 多人权限、责任归属、合规、有效期 |
| 项目工作区 | 当前材料、临时变量、输出和检查 | 项目隔离、交付格式、客户要求、保密范围 |

企业知识库可以被项目引用，项目变量不能自动写回企业知识库。个人知识库也可以有类似边界，但不必照搬企业目录或字段。

## 载体只是实现选择

Markdown、Obsidian、本地文件、云文档、数据库和搜索服务都可以承载这套框架。选择载体时看四件事：

- 人是否容易观察和修改；
- Agent 是否容易读取和写入；
- 来源、版本和权限是否能说明白；
- 系统失效时能否接管、迁移或重建。

本地 Markdown 适合用来做第一种可观察实现，但它不是共同框架本身。

## 共同验收

无论是什么场景，都至少检查：

- 材料没有因为整理失败而丢失；
- 人和 Agent 看到的内容没有形成两套互相漂移的版本；
- 可复用内容能说明来源和当前状态；
- 当前任务不会把临时信息悄悄写入长期内容；
- 找不到或无法确认时会明确报告缺口；
- 删除索引、关闭高级检索或更换 Agent 后，核心材料仍然可用。

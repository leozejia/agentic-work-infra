# Agentic Work 的共同模型

## 这是什么项目

Agentic Work Infra 研究一件共同的事：

> **人和 Agent 如何共享材料、工作规则和当前任务，完成一个可检查、可继续使用、失败后可以接管的结果。**

这不是某个知识库产品，也不绑定某个 Agent、模型、编辑器或云服务。企业知识库、个人知识库、投标、研发、客服和内容生产，都是用来检验这套共同模型的不同场景。

## 每个真实任务都要回答四个问题

### 1. 知道什么

任务会用到哪些材料：原始文件、笔记、历史记录、外部输入、数据或已有结果。

材料可以很乱，但要知道它是原件、整理结果、当前草稿，还是已经确认可以复用的内容。

### 2. 怎么做

任务要遵循哪些规则：Skill、流程、模板、检查要求、停止条件和人工确认点。

规则应该帮助 Agent 稳定完成工作，不应该替人做没有依据的判断。

### 3. 现在做什么

当前任务有哪些输入、临时变量、工作范围和输出位置。

当前任务的内容可以引用长期材料，但不能因为一次任务就悄悄改写长期材料。

### 4. 怎么确认

结果是否完整、来源是否可靠、状态是否清楚、谁需要确认、失败后能否继续。

成功提示、文件存在或 Agent 说“完成了”都不够。要检查用户真正需要的结果。

## 共同框架与场景区别

不同场景共享下面这条底层流程：

```text
接收材料
  ↓
理解和整理
  ↓
形成可复用内容
  ↓
在当前任务中引用
  ↓
检查结果和来源
  ↓
更新、替代或停止使用
```

共享的是问题和边界，不是固定目录和字段。

| 共同问题 | 个人场景可能关注 | 企业场景可能关注 |
|---|---|---|
| 谁可以使用 | 本人和个人偏好 | 多人权限和责任归属 |
| 哪些内容可复用 | 个人长期参考 | 公司正式材料和业务标准 |
| 如何判断仍然有效 | 个人判断和更新时间 | 版本、有效期、审批和合规 |
| 当前任务如何隔离 | 当前写作或研究 | 客户、项目、合同和承诺 |
| 结果如何确认 | 自己检查是否够用 | 业务负责人、审计和交付标准 |

因此，场景自己的目录、字段和状态命名只能留在场景层。

## 项目中的三个角色

- **知识库**：管理可以被持续引用的材料和结论。
- **Skill**：说明一类工作应该怎样做、怎样检查和何时停下。
- **Agent**：在当前任务中执行这些工作。具体选哪个 Agent，由任务需要决定。

它们不是三套互相替代的系统：知识库保存“有什么材料和结论”，Skill 规定“如何使用它们完成工作”，任务工作区保存“这一次具体发生了什么”。

## 不可丢掉的共同边界

- 原始材料和自动生成结果分开，失败时可以回到原始材料。
- 重要结论能回到来源；风险越高，来源和确认越具体。
- 未知、冲突和待确认是合法状态，不能为了完整而猜成确定。
- 长期可复用内容与当前任务内容分开。
- 自动操作保留中间结果，不静默覆盖用户材料。
- Agent 只修改明确授权的范围。
- 高级索引、向量数据和生成结果都可以重建、替换或关闭。
- 结果由独立的业务检查确认，不能只看 Agent 自己的成功描述。

## 不预先规定的内容

本项目不预先规定：

- 必须使用 Markdown、Obsidian、某个云知识库或某个数据库；
- 必须采用某一套目录名、Frontmatter 字段或状态枚举；
- 必须使用向量数据库、RAG、知识图谱或本体论；
- 必须选择某一家 Agent、模型或客户端；
- 所有场景都要拥有同一套 Skill 清单。

这些选择要由真实场景的问题和验收结果决定。

## 如何判断一个场景是否符合共同模型

拿一项真实工作检查：

1. 人和 Agent 是否能看到同一批必要材料？
2. 是否能区分原始材料、当前工作和可复用结果？
3. 是否能说明 Agent 按什么规则工作？
4. 结果是否能回到来源并由人继续检查？
5. 失败后是否可以保留现场、人工接管并重新运行？
6. 换一个场景后，共同边界是否仍然成立？

如果只有企业投标能回答这些问题，说明我们写的是投标方案，不是共同模型。

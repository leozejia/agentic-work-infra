# 人机协同模型

## 第一性原理

> **Agent 时代，人和 Agent 协同的核心是：双方面对同一个工作状态，共同观测、操作、修正和演化，而不是各自维护一套。**

这条原则适用于任何类型的工作，不限于知识库、投标或某个具体业务。

## 为什么这条原则成立

Agent 能力强，但如果人看不到 Agent 在做什么，项目就容易跑偏——方向偏、事实偏、决策偏，而且难以发现。

根本原因不是 Agent 的能力问题，而是协同结构的问题：人和 Agent 各自维护了不同的工作状态。Agent 把结论存在向量数据库里，人把判断留在脑子里；Agent 整理了一套文件，人另外维护了一套台账。两套状态一旦分裂，人就失去了对 Agent 行为的真实观测能力。

**共同可观测，是人和 Agent 能够真正协同的前提。**

## 共同工作状态的三个层次

### 1. 工作状态本身：记录"这件事是什么"

工作状态是人和 Agent 共同维护、共同可见的事实层。它的形式可以是 Markdown 文件、数据库记录、代码仓库或其他结构，但必须满足：

- 人能直接看到、理解和修改；
- Agent 能读取、引用和操作；
- 重要结论能回到原始来源，可以被核对；
- 未知、冲突和待确认保持显式，不能被伪装成确定。

### 2. 工作规则：记录"应该怎么做"

Skill 和经过确认的长期工作规则，描述步骤、检查项、停止条件、权限边界和输出约束。

工作规则不存事实，也不替代工作状态。规则和事实分离，才能在不修改事实的情况下优化工作方式，也才能在规则变化时知道哪些事实不受影响。

### 3. 当前任务：记录"这一次发生什么"

客户、金额、工期、临时要求、当前草稿和本次交付物，属于当前任务工作区。任务可以引用长期工作状态和规则，但任务变量不能自动写回长期层。

## 协同边界

人和 Agent 的能力不同，协同要从这个差异出发设计，而不是让 Agent 模拟人、或者让人变成 Agent 的操作员。

**Agent 擅长**：快速处理大量信息、结构化提取、重复验证、执行明确步骤、发现不一致。

**人擅长**：判断结论是否足够稳定、裁定冲突、批准高风险决策、决定工作方向。

因此：

| 决策 | 负责方 | 理由 |
|------|-------|------|
| 确认长期结论 | 人 | Agent 无法判断一个结论是否足够稳定，可以长期使用 |
| 裁定冲突 | 人 | Agent 不能擅自择优 |
| 高风险修改 | 人批准后 Agent 执行 | 影响全局或难以恢复的决策 |
| 整理、检索、验证、建议 | Agent | 从工作状态中提取结构、找问题、提建议 |

**Agent 不是决策者，是执行者和发现者。** 把决策推给 Agent 或者让 Agent 默默绕过决策边界，都会破坏协同结构。

## 架构只有一条主线

工作过程中可以有候选、草稿和失败现场，用于回溯和重新运行。但这些中间产物不能演变成第二套长期真相：

- 工作状态是事实基础，不能和索引、缓存或生成结果各自说不同的话；
- 辅助工具（搜索索引、向量数据库、生成结果）可以删除后重建，不能成为独立的事实来源；
- 业务可以有过程，架构不需要中间真相。

## Track：原则在具体工作中的落地

每个研究课题（track）是通用协同模型在一类具体工作中的验证和实现。Track 可以增加自己的工作状态格式、字段、工具、权限和 Skill，但不能违反通用原则，也不能把自己的实现方式提升为全局要求。

| 维度 | 通用原则 | Track 自行决定 |
|-----|---------|--------------|
| 工作状态 | 人和 Agent 共同可观测、可操作、可修正 | 格式、字段、目录结构 |
| 工作规则 | Skill 与确认的长期规则 | 业务步骤、审批条件、停止规则 |
| 当前任务 | 独立工作区、可引用、不可自动反写 | 任务变量的具体形式 |
| 辅助工具 | 可重建、不成为第二真相 | 具体工具和触发条件 |

## 判断是否仍在主线上

1. 人和 Agent 是否面对同一个工作状态？
2. 人能否直接看到、理解并修改这个状态？
3. 未知和冲突是否保持显式，没有被伪装成确定？
4. 当前任务的变量是否和长期工作状态分开？
5. 删除辅助工具后，工作状态是否仍然完整可用？
6. 出现问题时，人能否直接接管，不依赖 Agent 的上下文？

如果其中任何一条的答案需要"另一套隐藏系统"才能成立，协同结构已经偏离主线。

# Agent 项目协同规范

适用范围：使用 Agent 参与日常开发和维护的所有项目，不限于本仓库。

---

## 核心原则

**代码即事实，运行结果是最终判断标准。** 不接受 Agent 声称完成、日志看起来正常、文件存在等表象作为验收依据。任何工作结果必须能被人独立检查。

**共同可观测，不分裂成两套状态。** Agent 整理的内容、写的代码、做出的判断，必须对人直接可见。不接受 Agent 在不透明的索引、缓存或生成结果中维护一套人无法核对的状态。

**先从目标出发，不打补丁。** 遇到问题先找根本原因，再决定如何修改。连续两次对同一问题打局部补丁，说明根因没找到，需要重新分析。

---

## AGENTS.md 的职责

每个项目的 `AGENTS.md` 是 Agent 进入项目时的唯一入口，负责：

- **项目定位**：这是什么项目，不是什么
- **架构约束**：不可违反的边界，5条以内，每条一句话
- **修改和验证**：运行什么命令验证修改
- **文档路由**：任务需要的核心文件在哪里

`AGENTS.md` 不放：相关历史、benchmark 结果、详细架构说明、一次性任务记录、Handoff 内容。这些内容放到对应的专门文档。

**长度指导**：50行以内覆盖大部分项目；复杂项目上限100行。超过时先检查是否有内容该移到专门文档。

---

## 文档分工

| 文档 | 负责的问题 | 不要放的内容 |
|-----|----------|------------|
| `AGENTS.md` | 约束和路由 | 历史、解释、Handoff |
| `README.md` | 项目是什么，从哪里开始 | 架构细节、实现原理 |
| `docs/core/` | 跨场景成立的核心原则 | 场景特有内容、实现细节 |
| `docs/governance/` | 如何协同工作 | 业务逻辑、场景实现 |
| `HANDOFF.md` | 当前状态和下一步 | 长期原则、架构决策 |
| `docs/architecture/` | 架构设计和决策记录 | 运行命令、环境配置 |

判断规则：**三个月后这条内容还成立吗？** 成立的放 `AGENTS.md` 或核心文档；不成立的放 Handoff 或任务记录。

## 日常协同

### 开始工作前

```bash
git status --short --branch -uall
git log --oneline -5
```

先看当前状态，不依赖记忆。读相关代码再改，不猜。

### 修改代码

- 按现有模式写，不引入新的约定
- 每次修改范围尽量小，可独立验证
- 不改不该改的地方，即使看起来可以顺手优化

### 修改后验证

```bash
git diff --check       # 空白字符问题
git diff               # 确认改了什么
```

运行项目自己的测试和 lint。链接和文件路径改变时检查引用是否一致。

### 提交

commit message 说清楚改了什么，不说为什么改（代码本身应该能说清楚）。

## 人机分工

| 决策 | 谁来做 | 理由 |
|-----|-------|------|
| 确认长期结论、合并到主线 | 人 | Agent 无法判断结论是否足够稳定 |
| 裁定冲突，多个版本择一 | 人 | Agent 不能擅自择优 |
| 高风险修改：删目录、重构架构 | 人批准后 Agent 执行 | 影响全局或难以恢复 |
| 整理、检索、验证格式和链接 | Agent | 重复性机械工作 |
| 发现问题、列出选项和影响 | Agent | 快速扫描和分析 |

**Agent 不是决策者**：发现冲突时列出所有版本和来源，让人裁定；不确定时显式标出，不猜测并伪装成确定。

## 验证工作结果

业务结果是最终判断标准：

```text
预期的用户
  → 通过正式入口提供真实输入
  → 完成一段真实工作
  → 得到可检查、可继续使用的结果
```

以下信号不是单独的成功证据：接口返回 200、进程退出 0、Agent 声称完成、文件存在、日志看起来正常。

**验证分层：**

```text
类型检查 / lint
  快速排除明显的静态错误

单元测试
  纯逻辑、边界值、确定性状态转换

集成测试
  真实依赖、持久化、失败和恢复

E2E（真实入口 + 真实数据）
  业务整体是否成立
```

不能用其中一层代替另一层。"单测全绿"不代表业务成立。

### Agent 调试时的三个观察面

独立互相校验，不能依赖同一条信号：

- **行动面**：通过正式入口推进（UI、CLI、公开 API）；不为测试新增内部接口
- **观察面**：独立证据判断系统发生了什么（日志、进程、文件、数据库只读查询）；默认只读，不制造状态
- **判定面**：按业务承诺检查结果，不只看成功提示

**失败时先保留现场。** 不要立即清缓存、换假数据或无限重试。先判断问题在哪一层（环境、安装、运行时、业务逻辑、展示层），再针对性修复。

## 架构选择原则

新增任何依赖、服务、抽象或目录前，先回答：

1. 它解决了哪个已经出现的真实问题？
2. 它增加了什么成本（维护、认知、运行、变更）？
3. 不加它，什么会坏？

找不到第1条的答案，就不加。"以后可能用到"、"看起来更完整"不是理由。

**过度设计的信号**：为假想需求提前建系统；每个变化都抽象成框架；内部状态被暴露成用户概念；设计了大量精心维护的中间状态。

**过度简化的信号**：为了少写代码砍掉安全边界；把"能跑"误判为"设计正确"；把长期数据、权限和配置混在一起。

## 常见陷阱

**AGENTS.md 写成日志**：把任务记录、测试结果、一次性 Handoff 写进去。3个月后还成立的才放。

**打补丁代替解决问题**：连续对同一症状打局部补丁。根因没找到，重新分析。

**验证走捷径**：Agent 声称完成就接受。用真实入口和真实数据验证。

**架构分叉**：辅助工具（缓存、索引、生成结果）演变成独立的事实来源，和主状态说不同的话。

**不确定伪装成确定**：Agent 猜了一个字段值或判断，没有显式标出。遇到不确定，说出来。

**改动范围蔓延**：修一个 bug 顺手重构了三个文件。改动范围保持最小，可独立验证。

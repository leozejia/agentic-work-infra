# Agent 项目协同规范

适用范围：使用 Agent 参与日常开发和维护的所有项目，不限于本仓库。

## 如何使用本规范

**新建项目骨架**，按顺序执行：

1. 用 `templates/agents-md.md` 创建项目根目录的 `AGENTS.md`，填写项目角色和特有约束
2. 创建 `README.md`：一句话说这是什么，加常用命令
3. 用 `templates/handoff.md` 创建 `docs/HANDOFF.md`，填写当前状态
4. 按需建目录（有内容再建，不建空目录）：`docs/architecture/`、`docs/product/`、`docs/research/`
5. 运行 `git status` 确认没有多余的未跟踪文件

骨架就位的判断标准：Agent 拿到这个项目，读完 `AGENTS.md` 和 `docs/HANDOFF.md`，不需要其他信息就能开始第一个任务。

**开始任务**：先读项目 `HANDOFF.md` 确认当前状态 → 用 `templates/task-contract.md` 写任务定义，人确认后执行。

**遇到问题**：返回本文档的对应原则，不要打补丁。

---

## 核心原则

**代码即事实，运行结果是最终判断标准。** 不接受 Agent 声称完成、日志看起来正常、文件存在等表象作为验收依据。任何工作结果必须能被人独立检查。

**共同可观测，不分裂成两套状态。** Agent 的代码、判断和整理结果必须对人直接可见。不接受 Agent 在不透明的索引、缓存或生成结果中维护一套人无法核对的状态。

**先从目标出发，不打补丁。** 遇到问题先找根本原因，再决定如何修改。连续两次对同一问题打局部补丁，说明根因没找到，需要重新分析。

---

## AGENTS.md 的职责

每个项目的 `AGENTS.md` 是 Agent 进入项目时的唯一入口，负责：

- **项目定位**：这是什么项目，不是什么
- **架构约束**：不可违反的边界，5条以内，每条一句话
- **修改和验证**：运行什么命令验证修改
- **文档路由**：任务需要的核心文件在哪里

`AGENTS.md` 不放：历史记录、benchmark 结果、详细架构说明、一次性任务记录、Handoff 内容。

**长度指导**：50行以内覆盖大部分项目；复杂项目上限100行。超过时先检查是否有内容该移到专门文档。

## 文档分层

```text
AGENTS.md            项目宪法，短而稳定
README.md            人类入口，说明项目和常用操作
docs/HANDOFF.md      当前状态、下一步、交接
docs/product/        产品原则、PRD、商业模式、交互决策
docs/architecture/   架构设计、ADR、迁移方案
docs/research/       调研、benchmark、验收矩阵
apps/*/README.md     子应用运行、构建、测试命令
```

判断规则：稳定原则放 `AGENTS.md`；当前状态放 `HANDOFF.md`；长期设计放 `architecture`；产品判断放 `product`；证据和实验放 `research`；命令放最近的 `README.md`。

每次修改 `AGENTS.md` 前先问：**这条内容三个月后还应该存在吗？** 否定则不进 `AGENTS.md`。

### 文档写作原则

文档是工作状态的投影，不是工作过程的记录。

**写之前先问**：有人（或 Agent）三个月后需要这个信息才能做决策吗？否则不写。

**每份文档只回答一个问题**。写完后问：删掉这份文档，什么决策会变差？答案是"没有"则删掉。

**更新优先于新建**。能加进现有文档的内容，不单独建文件。能加一行的不写一节。

**不留占位符**。不创建内容为"待补充"的文件，不建没有文件的空目录。

**结论和理由，不是过程**。ADR 写"做了什么决策、为什么、代价是什么"，不写讨论过程。调研写"结论和支撑证据"，不写流水账。

## 工作方式

### 开始工作前

```bash
git status --short --branch -uall
git log --oneline -5
```

先看当前状态，不依赖记忆。读相关代码再改，不猜。

### 写代码

- 按现有模式写，不引入新的约定
- 每次修改范围尽量小，可独立验证
- 不改不该改的地方，即使看起来可以顺手优化

### 何时停止

遇到以下情况停下来等待人的判断，不能自行决定继续：

- 需要修改授权范围之外的文件
- 连续两次对同一症状打局部补丁
- 发现会影响生产数据或不可逆操作的风险
- 发现冲突的事实或版本，需要人裁定

### 提交

```bash
git diff --check
git diff
```

运行项目自己的测试和 lint。commit message 说清楚改了什么；链接或文件路径变更时检查引用是否一致。

## 人机边界

| 决策 | 谁来做 |
|-----|-------|
| 确认长期结论、合并到主线 | 人 |
| 裁定冲突，多个版本择一 | 人 |
| 高风险修改：删目录、重构架构 | 人批准后 Agent 执行 |
| 整理、检索、验证格式和链接 | Agent |
| 发现问题、列出选项和影响 | Agent |

发现冲突时列出所有版本和来源，让人裁定。不确定时显式标出，不猜测并伪装成确定。

## 开发约束

以下约束从第一性原理直接推出，适用于设计、开发和调试的全过程。

**不允许 mock**。Mock 测试的是你以为系统的行为，不是系统实际的行为。Mock 通过只说明假设成立，不说明业务成立。唯一例外：对外部付费 API（短信、支付网关）的单元测试可以 stub，但 E2E 验收必须用真实调用。

**不允许中间态**。中间态是设计没有想清楚的症状，不是过渡方案。如果需要中间态，说明目标状态还没有定义清楚，应该先讨论清楚再动手，不把中间态提交进主线。

**不允许模拟环境作为验收**。staging、docker-compose、headless runner 可以用于开发期快速排查，不能作为任务完成的证据。验收只在真实入口 + 真实数据 + 真实机器上进行。

**单元测试只测纯逻辑**。解析器、算法、边界值、确定性状态转换。不用单元测试覆盖 I/O、网络、数据库、文件系统，不用单元测试代替集成验证。

**过度设计和中间态是同一个问题的两面**。两者都是目标不清晰的信号。发现这两种情况时，先退回去讨论目标，再推进实现。

## 验证

业务结果是最终判断标准：

```text
预期的用户
  → 通过正式入口提供真实输入
  → 完成一段真实工作
  → 得到可检查、可继续使用的结果
```

以下信号不是单独的成功证据：接口返回 200、进程退出 0、Agent 声称完成、文件存在、日志看起来正常。

验证分层，不能用其中一层代替另一层：

```text
类型检查 / lint        快速排除明显的静态错误
单元测试              纯逻辑、边界值、确定性状态转换
集成测试              真实依赖、持久化、失败和恢复
E2E（真实入口 + 真实数据）  业务整体是否成立
```

## 调试

三个观察面独立互相校验，不能依赖同一条信号：

- **行动面**：通过正式入口推进（UI、CLI、公开 API）；不为测试新增内部接口
- **观察面**：独立证据判断系统发生了什么（日志、进程、文件、数据库只读查询）；默认只读，不制造状态
- **判定面**：按业务承诺检查结果，不只看成功提示

**失败时先保留现场**。不要立即清缓存、换假数据或无限重试。先判断问题在哪一层：

```text
setup        环境、依赖、权限、网络
install      安装包、签名、缓存、版本残留
runtime      进程、会话、超时、退出码
product      业务状态、数据所有权、任务和产物
presentation UI 映射、渲染、刷新
quality      结果完整性、事实、格式、实际可用性
```

层与层不能互相归因：UI 显示失败不能自动归因于账号或网络；环境权限失败不算产品逻辑失败。

**定位根因**：先找参考基线——最后正常版本、正常的相邻入口、或最小独立复现。写出可证伪的根因：

> 当 `<条件>` 发生时，`<所有者>` 因为 `<错误机制>` 没有完成 `<责任>`，所以用户看到 `<症状>`。

**修正责任边界，不修饰症状**。正确修复是恢复正式所有者应承担的生命周期：

- 恢复官方进程行为，而不是另造状态机
- 合并重复真相源，而不是同步它们
- 删除伪成功 fallback，而不是增加更多成功条件
- 修复输入或写入边界，而不是在输出端补内容

同一症状修复后再次出现，停止局部补丁，重新检查真相源、责任所有者和产品目标。

## 架构选择

使用最小但正确的设计（Correct Simplicity）。不追求最大抽象，也不追求最少代码。目标是当前阶段下最合身的设计：边界正确、复杂度足够、未来变化成本可控。

做架构加减法前，必须回答：

1. 这个设计解决了什么真实问题？
2. 它增加了什么成本？（维护、认知、运行、变更、包体、验证）
3. 它让哪个未来变化更便宜？
4. 选更小的方案，什么会坏？
5. 选更大的方案，什么会坏？

找不到第1条的答案，就不加。如果一个边界是产品质量、安全或长期可维护性的支点，就应该保留，即使它增加了一点复杂度。

**抽象的时机**：单一场景直接实现；抽象延迟到第二个真实用例出现时才引入。

**内部删除优于兼容**：内部实现重构时直接删除过时代码，不增加兼容层或双写逻辑。对外稳定接口（API、数据库协议、消息格式）的兼容性属于合同义务，单独评估，不在此限。

**过度设计的信号**：为假想需求提前建系统；每个变化都抽象成框架；内部状态被暴露成用户概念；设计了大量中间状态。

**过度简化的信号**：为了少写代码砍掉安全边界；把"能跑"误判为"设计正确"；把长期数据、权限和密钥混在一起。

### 依赖进入系统的标准

新增依赖前，至少满足以下一条：

- 明显降低包体、性能、稳定性或维护成本
- 提供项目无法低成本自研的成熟能力
- 是平台官方推荐路径
- 是产品质量或安全边界所需
- 显著减少长期变更成本

以下不是理由："以后可能会用"、"看起来更工程化"、"别的项目都这么做"、"框架更完整"、"Agent 写起来更顺手"。

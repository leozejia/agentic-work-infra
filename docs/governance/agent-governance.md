# Agent Governance

更新时间：2026-05-26

这份文档是写作和审计项目 `AGENTS.md` 时使用的母版。

每个项目可以有自己的 `AGENTS.md`，但项目内的 `AGENTS.md` 只应该写项目级约束，不应该回挂这份文档、复制这份文档，也不应该变成 handoff、README、运行手册或历史日志。

Agent 进入一个具体项目时，不应该被要求来回跳转读取这份全局文档。全局规范的作用是塑造项目 `AGENTS.md` 的写法，而不是成为每个项目运行时上下文的一部分。

## 1. AGENTS.md 是宪法，不是日志

优质的 `AGENTS.md` 应该短、稳定、可执行。

目标长度：

- 推荐：120-180 行
- 硬上限：300 行

允许放：

- 项目使命
- 关键读文档顺序
- 不可违背的产品原则
- 不可违背的架构原则
- 当前阶段的一句话指针
- 验证入口指针

不要放：

- phase 历史
- benchmark 结果
- 截图路径
- 长命令列表
- 本地 corpus 清单
- 文件大清单
- 详细架构解释
- 具体 smoke 输出
- 一次性任务 handoff
- 项目实现流水账

这些内容应该放到与项目实际结构相符的专门文档中。目录名不是规范本身：当前仓库用 `docs/core/` 保存共同模型，用 `docs/scenarios/` 保存具体场景，用 `docs/governance/` 保存治理方法。工程交接、运行命令和实验记录只有在确实存在时才建立对应文档，不为了凑结构提前创建目录。

## 2. AGENTS.md 推荐结构

```md
# <Project> Agent Guide

## Role

这个项目是什么，不是什么。

## Read Order

1. README.md
2. 项目共同模型
3. 当前任务需要的 Skill 或场景文档

只列真正需要先读的 5-8 个入口文件。

## Product Invariants

不可违背的产品原则。

## Architecture Invariants

不可违背的架构原则。

## Current Direction

当前阶段一句话。
细节指向项目实际存在的核心或场景文档。

## Do Not

高风险禁区。

## Verification

只写验证入口。
具体命令放 README 或 handoff。
```

## 3. Correct Simplicity

使用最小但正确的设计。

不要追求最大抽象，也不要追求最少代码。目标是当前产品阶段下最合身的设计：边界正确、复杂度足够、未来变化成本可控。

一个依赖、抽象、服务、队列、数据库、运行时或协议，只有在它能降低真实成本时才应该进入系统。

真实成本包括：

- 用户风险
- 安全风险
- 维护成本
- 变更成本
- 包体成本
- 运行成本
- 验证成本
- 认知成本

但不要为了看起来简单而删掉必要结构。如果一个边界是产品质量、安全、迁移、测试或长期可维护性的支点，就应该保留，即使它增加了一点复杂度。

做架构加减法前，必须回答：

1. 这个设计解决了什么真实问题？
2. 它增加了什么成本？
3. 它让哪个未来变化更便宜？
4. 如果选择更小的方案，什么会坏？
5. 如果选择更大的方案，什么会坏？

选择最小充分正确的设计。

## 4. 反对两种坏倾向

### 过度设计

表现：

- 为假想未来提前造系统
- 把每个变化都抽象成框架
- 把内部状态暴露成用户概念
- 为了“完整”引入服务、队列、数据库、插件系统

处理：

- 要求给出真实用户问题或真实维护成本
- 找不到证据就砍掉
- 先用文档记录未来方向，不急着实现

### 过度简化

表现：

- 为了少写代码砍掉安全边界
- 为了少依赖破坏产品质量
- 为了快，把长期数据、权限、密钥、迁移路径混在一起
- 把“能跑”误判成“设计正确”

处理：

- 先识别不可丢失的边界
- 对安全、数据、支付、用户资产、迁移路径保持保守
- 如果小方案让未来修复成本爆炸，就不是好方案

## 5. 依赖进入系统的标准

新增依赖前，必须满足至少一个条件：

- 明显降低包体、性能、稳定性或维护成本
- 提供项目无法低成本自研的成熟能力
- 是平台官方推荐路径
- 是产品质量或安全边界所需
- 能显著减少长期变更成本

依赖不应该因为这些理由进入：

- “以后可能会用”
- “看起来更工程化”
- “别的项目都这么做”
- “框架更完整”
- “agent 写起来更顺手”

如果系统原生命令或平台能力能以更小成本满足需求，可以优先使用原生能力。前提是它不破坏安全、可移植性和验证能力。

## 6. 文档分层

不要把所有信息写进一个文件。

推荐分层：

```text
AGENTS.md
  项目宪法，短而稳定

README.md
  人类入口，说明项目是什么和从哪里开始

docs/core/
  共同模型和长期设计

docs/scenarios/
  企业、个人、投标等场景材料

docs/governance/
  治理方法和验证方法
```

判断规则：

- 稳定边界放 `AGENTS.md`
- 项目入口放 `README.md`
- 跨场景原则放 `docs/core/`
- 场景细节放 `docs/scenarios/`
- 治理和验证方法放 `docs/governance/`
- 只有真实需要时才增加 handoff、脚本或应用目录

## 7. 项目 AGENTS.md 不要回挂全局规范

不要在项目 `AGENTS.md` 里写这种内容：

```md
## Global Agent Rules

Follow the global governance in:

`/Users/zejiawu/Projects/Project-Atlas/ganfan-dev/docs/agent-governance.md`

This project AGENTS.md only contains project-specific constraints.
```

这会制造无意义的索引跳转，让 agent 在项目上下文和全局上下文之间来回翻页。

正确做法：

- 用这份文档审计和改写项目 `AGENTS.md`
- 把真正需要长期执行的原则直接沉淀进项目 `AGENTS.md`
- 项目 `AGENTS.md` 自己闭环，不依赖外部回挂
- 不复制全局长文
- 不要求执行任务的 agent 读取全局母版

如果项目约束和全局规范冲突：

1. 先指出冲突
2. 判断项目是否有更强理由
3. 必要时更新项目文档或全局文档
4. 不要静默覆盖

## 8. 修改 AGENTS.md 的规则

允许修改：

- 新增真正稳定的项目原则
- 删除已经迁移到 handoff/architecture/research 的细节
- 更新 read order
- 更新当前阶段的一句话指针

不允许修改：

- 把一次性任务结果塞进去
- 把某次测试输出塞进去
- 把详细命令手册塞进去
- 把尚未定型的想法写成硬规则
- 为了让当前实现合理而改原则

每次修改 `AGENTS.md` 前，先问：

> 这条内容三个月后还应该存在吗？

如果答案是否定的，它不应该进 `AGENTS.md`。

## 9. Handoff 的边界

Handoff 可以细，但不能伪装成原则。

好的 handoff 应该包含：

- 当前状态
- 下一步
- 关键文件
- 不要改的范围
- 验证命令
- 已知风险

Handoff 可以过期。`AGENTS.md` 不应该频繁过期。

## 10. 一句话版

`AGENTS.md` 管原则，`HANDOFF.md` 管当前，`architecture` 管设计，`research` 管证据，`README` 管入口和命令。

架构选择遵循 Correct Simplicity：不追求最大抽象，也不追求最少代码，只追求当前阶段下最小充分正确的设计。

# Agent 自主调试与真实 E2E 规范

更新时间：2026-07-17

这份文档规定如何让 Agent 在真实运行环境中像用户一样推进业务、独立观察系统事实、判断最终结果，并在失败后定位根因。

真机 E2E 是产品验收，不是单元测试的替代品。单元测试、集成测试、headless 检查和源码运行负责快速发现确定性问题；只有正式入口、真实环境、真实输入和用户可检查交付物能够证明业务成立。

## 1. 业务结果是最终判定标准

开始调试前，先把产品目标写成一条完整业务承诺：

```text
某类用户
  -> 通过正式入口提供真实输入
  -> 完成一段真实工作
  -> 得到可检查、可继续使用的结果
```

测试章程至少说明：

- 用户最终想完成什么，而不是要点哪些按钮；
- 输入、账号、环境和历史状态来自哪里；
- 什么交付物才算成功；
- 哪些质量底线、风险和持久化事实必须成立；
- 本轮最值得攻击的失败假设；
- 哪些情况必须停止，哪些失败可以继续调查。

页面能打开、接口返回 200、进程退出 0、Agent 声称完成、文件非空或截图看起来正常，都不是单独的业务成功证据。

## 2. 自主调试需要三个观察面

Agent 自主调试不是随机点击，也不是只跑自动化脚本。它需要同时具备三个互相校验的面：

### 行动面

Agent 通过用户或正式调用者真正使用的入口推进业务：UI、正式 CLI、公开 API、产品已有的 MCP、系统分享入口或移动端交互。

行动面因产品而异。不要为了测试给普通软件新增 MCP、内部 RPC、数据库写入口或测试专用业务接口。如果产品本来就面向 Agent 并正式提供 MCP/API，测试应使用它；否则应通过真实 UI 或其他正式入口行动。

### 观察面

Agent 使用独立证据判断系统实际发生了什么：

- 页面、窗口、系统弹窗和通知；
- 网络请求和公开 API 状态；
- 进程树、退出码、资源使用和存活状态；
- 应用日志、诊断包和结构化运行事件；
- 用户目录、项目文件、数据库只读查询和最终产物；
- 重启后的恢复结果。

观察面可以适度白盒，但默认只读。它用于解释行为，不能绕过产品入口制造状态、补数据或把失败改成成功。

### 判定面

Agent 按业务承诺检查结果：内容是否完整、来源是否正确、文件能否打开、用户能否继续编辑、费用和状态是否一致、重启后是否保留、跨用户或跨项目是否污染。

行动、观察和判定不能依赖同一条信号。UI 显示成功时仍应检查正式状态和产物；文件存在时仍应检查内容、结构和用户可用性。

## 3. 具体产品选择具体工具

不存在通用的 GUI 自动化工具栈。优先使用当前 Agent 环境已经稳定提供的能力，再按产品表面选择：

| 产品表面 | 行动工具 | 主要观察工具 |
| --- | --- | --- |
| Web 应用 | 内置 Browser；需要现有登录态时使用 Chrome | DOM、网络、控制台、服务日志、数据库只读查询 |
| Electron | Computer Use、系统键鼠、必要时 CDP | 窗口、CDP、进程树、AppData、项目文件、日志 |
| Tauri / 原生桌面 | Computer Use、系统辅助功能 | 窗口、系统日志、项目文件、SQLite 只读查询、进程 |
| CLI | 正式 CLI 和终端 | stdout/stderr、退出码、文件、进程和服务状态 |
| Agent 工具产品 | 正式 MCP/API/CLI | 调用记录、正式状态、持久化数据和 UI 投影 |
| 移动端 | 真机交互、ADB、Appium 或 XCUITest | 设备日志、网络、应用数据和重启状态 |

工具选择遵循以下规则：

- 内置 Browser 适合干净、受控的 Web 调试；Chrome 适合依赖用户现有登录态、标签页和扩展的路径。
- Computer Use 负责原生窗口、Electron/Tauri、系统文件选择器、安装器和跨应用流程。
- CDP、DOM 和 WebView inspector 可以辅助读取事实和驱动真实 UI，但不能直接调用内部 handler 制造验收状态。
- Playwright 只在项目已经拥有浏览器回归套件、DOM 断言或 CI 浏览器矩阵时使用；不因 Agent 调试而全局预装。
- 产品已经有正式机器入口时直接使用，不再用 GUI 重演同一业务；产品没有时，不为测试发明一个。

## 4. 每轮先写自适应测试章程

真实业务的组合无限，固定脚本无法覆盖全部。每轮根据代码变化、上次失败、目标平台和可用真实数据选择最有信息量的场景。

测试章程记录：

- 本轮变化可能破坏的用户结果和数据边界；
- 最可能发生、代价最高或最难被单测发现的失败；
- 为什么选择这组真实数据和历史状态；
- 哪些行为需要重复运行观察波动；
- 何时增加第二个样本，何时停止扩测；
- 时间、费用、账号、外部系统和不可逆操作边界。

通常先用一份信息密度高的真实样本深入完成整条链路。只有现有样本没有覆盖当前风险时才增加样本，不为了数量机械重复。

## 5. 固定本轮测试身份

打开产品前记录：

- commit、不可变安装包版本和校验值；
- 平台、系统版本、目标应用路径和进程；
- source、debug、installed 或 customer lane；
- AppData、缓存、账号、项目和后端环境；
- Agent、模型、Skill 或插件版本；
- 真实输入快照及其标识；
- 允许的费用、写入、发布和停止条件。

同一状态只允许一个应用实例或业务所有者。不要让 source app、已安装 app、headless runner 或第二个 Agent 同时操作同一项目。

先观察既有用户状态，再决定是否需要干净环境。清空缓存可以验证首次使用，但会掩盖升级、会话恢复、历史数据和迁移问题。真实客户状态与干净快照应作为两种不同测试，而不是互相替代。

## 6. Agent 自主 E2E 循环

### 6.1 进入真机前做低成本预检

运行与当前风险相关的最小单元测试、行为回归、类型检查、构建和安装校验。它们负责排除已知确定性错误，不负责宣布产品通过。

开发态 headless 或公开 API 测试只有在复用生产业务内核时才有意义。若它维护另一套实现，它会制造新的假绿灯。

### 6.2 从正式入口开始

启动唯一目标应用，确认版本、账号、配置和真实依赖。通过行动面创建或打开真实业务对象，不直接改数据库、调用私有 renderer handler 或复制已经处理好的状态。

### 6.3 让业务运行到真实终态

Agent 按正常用户意图推进，不按照内部模块清单逐项点亮。异步任务必须观察到成功、失败或明确可恢复状态；submitted、queued、页面转圈和暂时无输出都不是终态。

长任务期间持续检查进程、事件和产物变化。网络重连、前端断开或短暂无输出不等于进程死亡，不能因此自动重跑并制造重复业务。

### 6.4 检查交付物而不是成功提示

根据产品类型检查：

- 内容、结构、格式和来源是否满足业务目标；
- 文件是否真实存在、可解析、可打开、可继续编辑或播放；
- 正式状态、日志、费用、任务身份和产物是否一致；
- 用户输入和人工修改是否被保留；
- 不完整结果是否诚实暴露缺口，而不是伪装完成。

### 6.5 重启后复查

退出目标应用，重新打开相同账号和业务对象，确认状态、文件、预览、历史、未完成任务和错误证据仍然一致。需要恢复的任务应继续观察原任务，不能静默创建第二个任务。

### 6.6 按风险增加探索分支

主链通过后，不是机械遍历所有页面，而是攻击本轮最可能失败的边界：中途编辑、补资料、取消、断网、重开、重复提交、跨项目切换、不同编码路径、历史缓存或目标平台差异。

## 7. 如何最大化业务覆盖

页面覆盖率不能代表业务覆盖率。高价值场景来自业务状态变化：

| 场景 | 主要发现什么 |
| --- | --- |
| 一条完整黄金主链 | 产品承诺是否真的成立 |
| 真实历史状态升级 | 缓存、迁移、旧会话和兼容问题 |
| 中途用户修改或补输入 | 覆盖、竞态、revision 和真相源问题 |
| 取消、断网、关闭和重开 | 任务所有权、恢复和重复执行问题 |
| 缺失、损坏或矛盾输入 | 是否诚实失败、是否产生伪结果 |
| 两个项目、主体或账号 | 隔离、复用和跨域污染问题 |
| 同一输入重复运行 | 稳定性、幂等和质量波动 |
| 正式安装、升级和卸载 | 打包、权限、路径和用户数据问题 |

每轮不必全跑。测试章程根据改动影响选择主链和一到三个高风险分支；发布前再覆盖完整的产品级组合。

涉及 LLM 或生成式结果时，不能断言固定文本，也不能只让同一个执行 Agent 自我评价。判定至少分三层：

- 结构底线：必需章节、字段、媒体、引用、文件格式和可编辑性；
- 事实底线：来源一致、不编造、不跨主体污染、不丢用户修改；
- 业务质量：完整性、可用性、风险覆盖和用户需要修改的程度。

语义质量可以由独立会话、独立 Reviewer 或人工抽检判断，但最终仍要回到真实来源和用户交付物。

## 8. 失败后先保留现场

失败时停止在失败点，保存时间、页面、日志、项目、AppData、进程和产物。不要立即清缓存、换假数据、手工补状态、换入口或无限重试来制造通过。

先判断问题所在层：

```text
setup        环境、依赖、权限、网络、密钥
install      安装包、签名、缓存、用户目录、版本残留
runtime      进程、会话、协议、重连、超时和退出码
product      业务状态、数据所有权、任务和产物
presentation UI 映射、刷新、渲染和交互
quality      结果完整性、事实、格式和实际可用性
```

环境权限失败不能算产品逻辑失败；UI 显示失败也不能自动归因于账号、Key、模型或网络。先从独立观察面确认请求走到了哪一层。

## 9. 从现象收敛到根因

优先寻找参考基线：最后正常版本、官方工具行为、正常的相邻入口或最小独立复现。比较参数、生命周期、输入输出、持久化时机和结束条件，不凭记忆重写流程。

修改前写出可证伪根因：

> 当 `<条件>` 发生时，`<所有者>` 因为 `<错误机制>` 没有完成 `<责任>`，所以用户看到 `<症状>`。

然后做一个最有区分度的实验，例如：

- 同一真实输入比较正常版本和当前版本；
- 直接运行官方入口，区分平台问题与包装层问题；
- 检查进程是否仍存活、状态是否落盘、产物是否可解析；
- 绕过展示层只读正式状态，区分业务失败与 UI 映射；
- 用小输入和大输入、单文件和多文件做控制实验；
- 在保留原现场的前提下，用隔离用户目录区分缓存影响。

实验要能否定竞争假设。不要同时修改多层，也不要用刚修改的同一套代码制造结果并证明自己。

## 10. 修正责任边界，不修饰症状

正确修复通常是恢复正式所有者应承担的生命周期：

- 恢复官方进程或会话行为，而不是另造状态机；
- 合并重复真相源，而不是同步它们；
- 删除伪成功 fallback，而不是增加更多成功条件；
- 修复输入、参数或写入边界，而不是在输出端补内容；
- 保留原任务并恢复观察，而不是因页面断开自动重跑；
- 让正式业务状态驱动 UI，而不是让 UI 猜业务状态。

一轮修复后同一用户症状再次出现，停止局部补丁，重新检查真相源、责任所有者和产品目标。

## 11. 回归测试与真实 E2E 的分工

确定性缺陷应留下最窄行为回归：旧实现失败、新实现通过，并断言用户可观察行为或正式状态。异步问题测试完整生命周期；文件问题验证语义结构，不只验证存在和大小。

验证分层如下：

```text
单元测试
  纯逻辑、边界值、解析和确定性状态转换

集成 / 行为测试
  真实所有者、适配器、持久化、失败原子性和恢复

headless / source smoke
  开发期快速验证正式业务内核和可见投影

installed real-device E2E
  安装、权限、账号、真实数据、完整业务和最终交付
```

单测防止已知机制退化，真机 E2E 防止“每个模块都对，但业务整体不成立”。不能用其中一层代替另一层。

## 12. 为自主调试提供可观察性

产品应提供正常运行和支持所需的可观察性，而不是测试后门：

- 明确版本、环境、运行 ID、任务 ID 和终态；
- 有界、结构化并可导出的诊断信息；
- 可识别的正式项目目录、产物和日志；
- 真实错误分类，不把所有失败映射成同一条提示；
- 长任务的进程所有权、取消和恢复信息；
- 对密钥和用户隐私做必要脱敏。

这些能力首先服务用户支持和运行可靠性，也让 Agent 能独立判断事实。不要为自动化新增可写内部状态、隐藏管理员入口或第二套业务 API。

## 13. 证据记录

每次复杂真机调试至少保留：

```md
## Test Identity
版本、平台、应用路径、账号、配置、真实输入和授权边界。

## Test Charter
用户目标、风险假设、质量底线和停止条件。

## Observation
按时间记录操作、UI、进程、日志、正式状态和产物。

## Result
业务是否完成；哪些证据支持结论。

## Root Cause
失败时的一条可证伪因果描述。

## Fix And Regression
修复的责任边界；旧失败、新通过的回归证据。

## Real-Device Retest
同一正式入口和真实数据上的最终结果。

## Remaining Risk
仍未覆盖的状态、平台或质量风险。
```

失败尝试是证据，不要删除。文档保留结论和复现条件，原始大文件、用户数据和敏感日志留在受控本地位置，不提交仓库。

## 14. 完成条件

一次调试或发布验收只有同时满足以下条件才算完成：

- Agent 通过适合该产品的正式入口完成真实业务；
- 行动面、观察面和判定面的证据能够互相校验；
- 最终产物对用户真实可用，而不是内部成功状态；
- 用户输入、人工修改、费用和关键风险没有丢失或伪造；
- 退出重开后正式状态和产物保持一致；
- 失败根因已落在正确所有者，并有旧失败、新通过的回归；
- 对应目标平台、正式安装态和真实数据已复测；
- 未完成部分被明确记录，没有用 fallback、清缓存或换数据伪装通过；
- 扩测范围来自风险证据，没有演化成与目标无关的全面测试工程。

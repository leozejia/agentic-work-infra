# Skill 设计最佳实践

## 核心理念

**将 Skill 视为结构化的工作目录，而非冗长的提示词。**

遵循"渐进式披露"原则：AI先看元数据判断是否触发，再加载核心流程，执行时按需读取参考文档。

## Skill 标准结构

```
skill-name/
├── SKILL.md              # 入口：元数据 + 核心流程
├── references/           # 参考文档（按需加载）
├── scripts/              # 确定性脚本（保证稳定执行）
└── assets/               # 输出模板或静态资源
```

## SKILL.md 的两部分

### 1. 元数据（必需）

```yaml
---
name: skill-name
description: >
  做什么（一句话）
  什么时候用（触发条件）
  不适用于什么（边界）
---
```

**description 是关键**：它决定 AI 何时触发这个 Skill。必须写清楚触发条件，而不是功能介绍。

### 2. 正文（核心流程）

- 只写高层级流程和规则
- 不写细节（细节放 references/）
- 控制在 500 行以内
- 明确停止规则（什么情况下停下来问人）

## 最佳实践

### 精准的 description

**错误写法**：
```yaml
description: 这个Skill提供了完整的投标能力，支持多种招标文件格式
```

**正确写法**：
```yaml
description: >
  响应招标文件，从知识库提取内容组装标书。
  当用户要响应招标、生成标书、或提到"投标"时使用。
  不适用于知识库整理、文章写作等其他任务。
```

### 渐进式披露

不要把所有内容塞进 SKILL.md。合理分层：

| 内容类型 | 应该放在 | 原因 |
|---|---|---|
| 触发条件、边界 | 元数据 | AI决定是否使用 |
| 核心流程、路由 | SKILL.md 正文 | 执行框架 |
| 详细规范、示例 | references/ | 按需加载 |
| 确定性操作 | scripts/ | 保证稳定性 |

### 确定性操作用脚本

格式检查、文件解析、数据转换等必须精确执行的操作，应该用 scripts/ 里的脚本完成，不应该让 AI "看着办"。

### references/ 的组织

按**领域**组织，不是原子化拆分：

```
references/
├── 招标要求提取规则.md      # 一个领域
├── 内容检索规则.md          # 一个领域
└── 检查清单.md              # 一个领域
```

不要拆成几十个碎片文件，会增加路由复杂度。

## Skill 的迭代

Skill 不是一次性写完的规范，而是从真实任务中提炼、用反例持续修正。

### 迭代流程

1. **真实任务**：选一个真实场景
2. **执行**：让 AI 按当前 Skill 执行
3. **检查**：对照检查清单，记录问题
4. **分析**：规则不清楚？AI 理解错？还是规则有问题？
5. **修正**：更新 Skill，记录改了什么、为什么改
6. **验证**：用类似任务再跑一遍

### 迭代记录示例

| 版本 | 问题 | 改进 |
|---|---|---|
| 0.5.0 | 文件名太长 | 增加规则："最小可识别语义" |
| 0.6.2 | 表格被改成段落 | 增加规则："表格保持表格" |
| 0.7.1 | 缺少日期状态 | 明确要求："来源、日期、状态缺一不可" |

## 判断标准：适合做成 Skill 吗？

三个标准：

1. **重复性**：这项工作会反复发生吗？
2. **规则性**：有明确的规则吗？
3. **可检查**：结果能检查对错吗？

都满足才适合做成 Skill。

## 好 Skill vs 差 Skill

| 维度 | 好 Skill | 差 Skill |
|---|---|---|
| SKILL.md 长度 | < 500行 | 1000+行 |
| description | 触发条件+边界 | 功能介绍 |
| 确定性操作 | 交给 scripts/ | 写在正文 |
| 领域知识 | 外置到 references/ | 内联在 SKILL.md |
| 边界 | 明确"不适用于..." | 声称什么都能做 |
| 迭代 | 记录反例，持续改进 | 一次成功当最终版 |

## 一句话总结

Skill = 给 AI 的业务操作手册，从"每次都教"变成"教一次，用无数次"。

企业内部培训

Skill：给AI的业务操作手册

Agent工具可以换，但Skill是你的。它是企业AI能力的真正沉淀。

适用：需要定制AI工作方式的业务场景 读者：AI协调员、业务骨干

01Skill是什么

不是给人的操作手册，是给AI的。

Skill是给AI的业务操作手册。它规定了AI在特定场景下应该遵循什么规则、按什么步骤工作、如何检查结果、遇到异常怎么处理。

举例：知识库Skill教AI怎么整理企业资料——

  • 文件名应该怎么改（带上关键词、专有名词）
  • 内容怎么检查（表格保持表格、图片要保留）
  • 来源怎么标记（写明来源、日期、状态）
  • 失效的怎么处理（移到archive，不再被搜到）
  • 遇到冲突怎么办（两份资料说的不一样，停下来问人）

为什么不是"提示词"

很多人把Skill当成"一段很长的提示词"，这是错的。

Skill是结构化的工作目录，包含：

  • 元数据：什么时候触发这个Skill
  • 核心流程：应该按什么步骤干活
  • 参考文档：需要时查阅的领域知识
  • 确定性脚本：必须精确执行的操作

提示词是一次性的，Skill是可复用、可迭代的资产。

02为什么需要Skill

通用AI不懂你的业务，每次都从头解释太累。

没有Skill时

每次让AI干活，你都要解释一遍业务规则：

  • "整理这些文件，注意文件名要带上关键词"
  • "表格不要改成段落，会丢信息"
  • "最上面要标记来源、日期、状态"
  • "失效的移到archive目录"
  • "如果两份资料说的不一样，先问我"

每次都要重新说一遍，AI还不一定按你的标准做。

有Skill后

你只需要说："整理inbox"

AI自动加载知识库Skill，按既定规则干活：

  • 文件名怎么改 ✓
  • 内容怎么检查 ✓
  • 来源怎么标记 ✓
  • 失效的怎么处理 ✓
  • 遇到冲突怎么办 ✓

规则固化下来，每次都按同样的标准执行。

Skill = 把业务规则固化下来，从"每次都教"变成"教一次，用无数次"。

03一个Skill长什么样

Skill是一个工作目录，不是一个文件。

标准结构

knowledge-base/ # Skill名称 ├── SKILL.md # 入口文件：元数据 + 核心流程 ├── references/ # 参考文档（按需加载） │ ├── 命名规范.md │ └── 检查清单.md ├── scripts/ # 确定性脚本（保证执行结果稳定） │ └── 检查文件.py └── assets/ # 输出模板或静态资源 └── 报告模板.md

SKILL.md（入口文件）

这是AI看到的第一个文件。它分两部分：

1. 元数据（顶部）

--- name: knowledge-base description: > 帮用户整理知识库，让以后问问题时搜得到、打开能看懂。 当用户要建知识库、整理一批资料、把旧文档变成可检索的知识时使用。 不适用于写文章、做PPT、写代码等内容创作任务。 ---

description是关键：它决定AI什么时候触发这个Skill。必须写清楚：

  • 做什么（整理知识库）
  • 什么时候用（用户要建知识库、整理资料时）
  • 什么时候不用（不适用于写文章、做PPT）

2. 正文（核心流程）

正文只写高层级的流程和规则，不写细节。细节放在references里按需加载。

为什么要分开？

因为AI的上下文窗口有限。如果把所有细节都塞进SKILL.md，AI每次都要读完整篇（几千个token），很快就会撑爆窗口。

渐进式披露：先只看元数据（几十个token）判断要不要用这个Skill；确定要用后，加载核心流程；执行中需要时，再加载具体的参考文档。

04Skill怎么迭代

Skill不是一次性写完的规范，而是从真实任务中提炼、用反例持续修正的操作手册。

从0.5.x到0.8.x，迭代了什么

以知识库Skill为例，真实迭代过程：

版本遇到的问题改进
0.5.0 AI整理后的文件名太长，看不清重点 增加规则："文件名用最小可识别语义，不多写一个字"
0.6.2 表格被改成了段落，行列关系丢了 增加规则："表格保持表格，不要改成一段话"
0.7.1 AI标记了来源，但没写日期和状态 明确要求："来源、日期、状态三样缺一不可"
0.8.0 两份资料内容矛盾，AI自己选了一个，结果选错了 增加停止规则："遇到冲突停下来问人，不要自己猜"

每次迭代都是因为真实任务暴露了问题，然后修正规则。

错误的迭代方式

  • 没有真实任务，靠想象写规则
  • 一次成功就当成最终版本
  • 出了问题改提示词，不改Skill
  • 不记录反例，下次又犯同样的错误

正确的迭代流程

  1. 真实任务：选一个真实的工作场景（如整理10份投标资料）
  2. 执行：让AI按当前Skill执行
  3. 检查：对照检查清单，看哪些地方不符合标准
  4. 分析：是Skill规则不清楚？还是AI理解错了？还是规则本身有问题？
  5. 修正：更新Skill，记录这次改了什么、为什么改
  6. 验证：用类似的任务再跑一遍，确认问题解决了

Skill是活的，不是死的。每次真实任务都是一次测试，每个反例都是一次改进机会。

05哪些工作适合做成Skill

不是所有工作都适合做成Skill。判断标准有三条。

判断标准说明
重复性 这项工作会反复发生吗？如果只做一次，不值得做成Skill
规则性 这项工作有明确的规则吗？如果每次都不一样，无法固化
可检查 结果能检查对错吗？如果没法检查，就没法迭代改进

适合做成Skill的工作

适合 知识库整理
重复性：每周都要整理新资料
规则性：文件名规则、来源标记规则明确
可检查：搜得到、打开能看懂、有来源

投标响应编制
重复性：每月多个投标任务
规则性：章节结构、内容提取、格式转换有标准
可检查：覆盖所有要求、没有串项目、格式合规
不适合 创意文案写作
重复性：有
规则性：无，每次创意都不同
可检查：难，好坏是主观的

复杂决策
重复性：低
规则性：无，要综合大量不确定因素
可检查：难，只能事后看结果

一句话判断

如果你能对着一个新人说清楚"这项工作应该怎么做、做成什么样才算合格"，那就适合做成Skill。

如果你自己也说不清楚，或者每次做法都不一样，那就不适合。

06企业可以有哪些Skill

Skill不是越多越好，而是要真正有用。

当前已有的Skill

  • 知识库Skill：教AI整理企业资料，让人和AI都能搜到、看懂

规划中的Skill

  • 投标Skill：教AI从知识库提取内容、组装标书、检查合规性
  • 媒体生产Skill：教AI从正文衍生不同渠道的内容、保持一致性
  • 软件交付Skill：教AI按规范完成开发、测试、部署流程

你的业务需要什么Skill？

问自己三个问题：

  1. 哪项工作重复性最高、最消耗人力？
  2. 这项工作有没有明确的标准？
  3. 如果AI能按标准做这项工作，能节省多少时间？

从最痛的点开始

不要一次做十个Skill。先从最痛的一个点开始：

  • 选一项重复性高、规则明确、人工做很累的工作
  • 写出初版Skill（规则不需要完美）
  • 用真实任务测试，记录哪些地方不对
  • 迭代改进，直到AI能稳定产出合格结果
  • 再开始做第二个Skill

07Skill的价值

Skill是企业AI能力的真正沉淀。

为什么说Skill比Agent工具更重要？

对象能不能换说明
Agent工具
（Workbuddy、Claude、ChatGPT）		 能换 底层模型能力已经趋同，工具可以替换。半年后可能又有新工具
知识库 不能换 企业资质、业绩、技术能力是企业独有的，必须长期积累
Skill 不能换 你的业务规则、工作流程、质量标准是企业独有的，必须持续迭代
Agent工具会变，但知识库和Skill是企业在AI时代能积累的真家伙。

Skill库 = 企业的AI操作系统

随着Skill的积累，企业会形成自己的Skill库：

企业Skill库/ ├── knowledge-base/ # 知识整理Skill ├── bidding/ # 投标响应Skill ├── media-production/ # 媒体生产Skill ├── customer-service/ # 客服响应Skill └── ... # 更多业务Skill

这就是企业的AI操作系统：

  • 新员工入职，先学Skill库——这是公司的工作标准
  • AI干活，自动加载对应Skill——按同样的标准执行
  • 业务改进，更新Skill——所有人和AI同步更新

从"每个人有自己的做法"到"公司有统一的标准"，Skill让业务标准可以沉淀、复用、迭代。

08好Skill vs 差Skill

差Skill会让AI行为不可预测，好Skill让AI稳定产出合格结果。

差Skill的典型特征

反模式1：把SKILL.md写成长篇提示词

有人写了1200行塞满"请按以下规范输出""禁止使用以下表达"，结果AI加载后表现比裸调用还差。

为什么：SKILL.md越长，上下文窗口越容易撑爆，触发信号越容易被淹没。

反模式2：description写成功能介绍而非触发条件

错误写法："这个Skill提供了完整的投标能力，支持多种招标文件格式"

正确写法："当用户要响应招标、生成标书、或提到'投标'时使用"

为什么：AI决定触发的逻辑是后者，不是前者。

反模式3：多个Skill边界重叠

如果两个Skill的description都能覆盖同一类任务，AI会随机选择，导致行为不可预测。

反模式4：把确定性操作写在正文让AI"看着办"

例如：格式检查、文件解析、数据转换这些必须精确执行的操作，应该用scripts/里的脚本完成，不应该让AI每次"临场发挥"。

对比总结

维度好Skill差Skill
SKILL.md长度< 500行，只放流程和路由1000+行，塞满细节
description触发条件+边界功能介绍
确定性操作交给scripts/写在正文让AI"看着办"
领域知识外置到references/内联在SKILL.md
边界明确"不适用于..."声称什么都能做
迭代记录反例，持续改进一次成功就当最终版

09速查

培训结束后，记住这一页就够。

  1. Skill的定义：给AI的业务操作手册，规定AI在特定场景下应该遵循什么规则、按什么步骤工作。
  2. 为什么需要Skill：通用AI不懂你的业务，Skill把业务规则固化下来，从"每次都教"变成"教一次，用无数次"。
  3. Skill的结构：SKILL.md（入口）+ references/（参考文档）+ scripts/（确定性脚本）+ assets/（输出模板）。
  4. 元数据是关键：description决定AI什么时候触发这个Skill，必须写清楚做什么、什么时候用、什么时候不用。
  5. 渐进式披露：先只看元数据判断要不要用；确定用后加载核心流程；执行中按需加载参考文档。
  6. Skill怎么迭代：从真实任务中提炼，用反例持续修正。每次迭代记录改了什么、为什么改。
  7. 适合做成Skill的工作：重复性高、规则明确、结果可检查。创意性、决策性工作不适合。
  8. 从最痛的点开始：不要一次做十个Skill，先从最痛的一个点开始，迭代成熟后再做下一个。
  9. Skill是企业AI能力的沉淀：Agent工具可以换，但知识库和Skill是企业在AI时代能积累的真家伙。
  10. 好Skill vs 差Skill：SKILL.md要精炼、description写触发条件、确定性操作用脚本、持续记录反例改进。

下一步

今天讲了Skill是什么、为什么重要、怎么做。

现在你可以开始：

  1. 识别一项重复性高、规则明确的工作
  2. 写出这项工作的标准（怎么做、做成什么样才算合格）
  3. 用真实任务测试，记录哪些地方不符合标准
  4. 迭代改进，形成你的第一个Skill
Skill是活的，不是死的。持续从真实任务中改进，才能真正发挥价值。

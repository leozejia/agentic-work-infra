# 投标场景：知识库到标书工作流

> 本文是投标场景方案。它使用知识库共同框架，但其中的客户、金额、工期、企业资质和项目目录只适用于投标，不是全局模型。

## 先解决真正的卡点

企业用 Word 模板加 AI 复制粘贴，可以很快生成一份看起来完整的标书，但很难稳定重复：

| 问题 | 后果 |
|---|---|
| 每次都要重新读取整份大 Word | AI 反复猜哪些内容稳定、哪些已失效、哪些只适用于旧项目 |
| 原始证据、长期知识和项目变量混在一起 | 客户名、金额、参数和承诺容易串项目 |
| 一条知识更新后不知道影响哪些章节 | 商务、技术和附件之间可能出现不一致 |
| 格式提取正确不等于事实正确 | 标书排版合格，内容仍可能过期、冲突或没有来源 |

根因不是 Word 本身，而是不同性质的内容被绑在同一批文件里：

- 企业长期知识，例如资质、技术能力和已确认的业绩；
- 项目临时变量，例如客户名、金额、工期和本次承诺；
- 原始证据，例如合同、证书、验收材料和招标文件；
- 最终交付，例如已排版的 Word 或 PDF。

## 打通方案：企业知识、项目工作区和投标 Skill

### 架构

```text
business-root/
├── company-vault/
│   ├── inbox/       原始输入，允许混乱，也可以放候选笔记
│   ├── notes/       已确认、可复用的企业知识
│   └── archive/     已确认失效或被替代的知识内容
└── work/
    └── <具体项目>/  招标文件、项目变量、草稿和交付
```

企业知识库和项目工作区在同一业务根目录下并列，项目工作区不放进 `company-vault/`。`inbox/` 是原始资料的正式入口，不要求甲方先整理。可以有一份说明文件记录用途和边界，但不是必需层。

| 位置 | 内容 | 能否作为正式投标依据 |
|---|---|---|
| `company-vault/inbox/` | Word、PDF、Excel、图片、聊天记录、候选片段和候选笔记 | 不能，除非完成核对并进入 `notes/` |
| `company-vault/notes/` | 已确认的企业资质、技术能力、业绩案例和标准响应 | 状态、有效期和适用范围都满足时可以 |
| `company-vault/archive/` | 已确认失效或被替代的知识内容 | 不能 |
| `work/<具体项目>/` | 招标要求、客户、金额、工期、项目方案、草稿和最终交付 | 只对当前项目有效 |

项目可以引用 `company-vault/notes/` 中的知识。项目变量、草稿和审定结果不能自动写回企业知识。项目完成后，经过确认、允许复用的案例和实施经验，才重新整理成企业知识。

### 投标 Skill 的职责

1. 先把招标文件放入当前项目的 `work/<具体项目>/`；
2. 提取章节、资格条件、评分项、格式要求和截止时间；
3. 从 `company-vault/notes/` 查找 `state: verified`、未过期且时效已明确的适用内容；
4. 对每条企业事实保留笔记路径、原始文件和原文位置；
5. 把项目变量只写入当前项目工作区；
6. 按招标要求组装标书；
7. 检查漏项、冲突、失效材料、来源缺失和跨项目污染；
8. 缺少确认内容时标记缺口，不能自动补全；
9. 最后才转换为 Word 或 PDF，并保留可回溯的 Markdown 草稿。

## 分步实施

### 第一步：按资料归属接收原件

不从“把稳定内容从 Word 模板拆出来”开始，而从接住原始资料开始。进入哪里，先看它属于企业长期资料还是当前项目：

| 原始资料 | 进入位置 | 原因 |
|---|---|---|
| 企业证书、历史合同、验收材料、能力说明 | `company-vault/inbox/` | 可能形成跨项目复用的企业知识 |
| 当前招标文件、澄清文件、客户要求 | `work/<具体项目>/` | 只属于当前项目，不能污染企业知识 |
| 暂时无法判断归属的文件 | 先留在当前项目并标记待判断 | 不确定时先隔离，确认后再决定是否进入知识库 |

以企业交来一份 200 页综合材料为例：

1. 原文件原样放入 `company-vault/inbox/`；
2. Agent 盘点目录、章节、表格、图片和可能的内容类型；
3. 标出可能属于企业资质、业绩或技术能力的片段；
4. 在 `company-vault/inbox/` 中生成候选笔记，记录页码、章节或表格编号；
5. 人核对主体、日期、范围、有效性和是否允许复用；
6. 确认后的内容进入 `company-vault/notes/`，其余保留 `candidate` 或 `needs-review` 状态。

当前项目的招标要求始终留在 `work/<具体项目>/`。候选笔记保留在 `inbox/`，不能直接参与正式标书组装。正式笔记失效时进入 `archive/`，原始证据不随之移动。整理失败时，原文件和候选结果都要保留。

### 第二步：只把已确认内容写成企业知识

`notes/` 可以按实际取用方式组织，例如：

```text
company-vault/
├── inbox/
│   ├── 企业材料-最终版2.docx
│   └── 候选-2025某项目业绩.md
├── notes/
│   ├── 企业资质/
│   ├── 技术能力/
│   ├── 业绩案例/
│   └── 标准响应/
└── archive/
```

候选笔记示例：

```markdown
---
state: candidate
source: inbox/企业材料-最终版2.docx
source_location: page=43; table=项目业绩表
---

## 待核对结论

材料中出现某项目业绩记录，客户名称、验收日期和合同金额需要核对。
```

已确认笔记示例（`source` 使用 `company-vault/` 根目录相对路径，`source_location` 写成可复核定位）：

```markdown
---
state: verified
type: 业绩案例
source: inbox/企业材料-最终版2.docx
source_location: page=43; table=项目业绩表
owner: 市场部
valid_to: 2027-12-31
---

## 结论

某某公司于 2025 年完成某项目，已通过验收。

## 使用限制

投标文件必须同时核对合同或验收材料。
```

`state` 还可以是 `unknown`、`needs-review`、`superseded` 或 `archived`。没有来源、原文位置或确认记录的内容，不能伪装成 `verified`。

### 第三步：建立项目工作区

每次投标先建立独立的项目目录：

```text
work/
└── 2026-餐饮投标-A客户/
    ├── project.md          # 客户、金额、工期和当前承诺
    ├── requirements.md     # 招标要求和提取结果
    ├── selected-notes.md   # 本项目引用了哪些企业笔记
    ├── draft/              # Markdown 或其他中间草稿
    └── output/             # 最终 Word、PDF 和审定记录
```

`project.md` 只记录当前项目变量：

```markdown
---
project: 2026-餐饮投标-A客户
customer: A餐饮集团有限公司
amount: 380万元
schedule: 180天
---

## 项目特定要求

- 必须有餐饮行业业绩，不少于 3 个；
- 质保期 2 年；
- 需要驻场服务。
```

企业笔记可以被引用，客户、金额、工期和本次承诺只在当前项目生效。投标 Skill 需要检查这些变量是否完整、是否只出现在当前项目，以及是否被错误写回企业知识。

### 第四步：投标 Skill 初版

**Skill 结构**：

```text
tracks/bidding/
├── SKILL.md
├── references/
│   ├── 要求提取规则.md
│   ├── 内容检索规则.md
│   ├── 格式转换规则.md
│   └── 检查清单.md
└── scripts/
    ├── 提取招标要求.py
    ├── 转换为Word.py
    └── 检查标书.py
```

**核心流程**：

```markdown
1. 建立项目工作区，接收招标文件和项目变量
2. 提取招标要求，生成 requirements.md
3. 只从知识库检索 `state: verified` 且未过期、时效已明确的内容
4. 对每条企业事实保留 `source` 和可复核的 `source_location`
5. 缺少内容或遇到冲突时生成缺口清单
6. 组装 Markdown 草稿，不自动填补未知信息
7. 检查漏项、冲突、过期内容、来源和跨项目污染
8. 人确认后，再转换为 Word 或 PDF
```

停止规则：

- 招标要求无法完整提取；
- 知识库只有 `candidate` 或 `needs-review` 内容，没有 `verified` 依据；
- 两份企业知识互相冲突；
- 企业知识已过期或时效无法确认；
- 客户名、金额、工期或其他项目变量不明确；
- 原始证据和整理后的结论对不上；
- 当前用户是否有权读取或使用材料不明确。

### 第五步：用真实案例迭代

选一份真实招标文件，记录每次运行暴露的问题：

| 问题 | 应归到哪里修正 |
|---|---|
| 原始 Word 目录或表格没识别出来 | 内容盘点和抽取规则 |
| 候选业绩没有页码，无法核对 | 来源记录规则 |
| 检索到了待确认或过期内容 | 状态过滤和检查规则 |
| 缺少企业事实却被自动补全 | 缺口和停止规则 |
| Word 转换后表格错乱 | 格式转换脚本 |
| 两个项目出现同一客户名或金额 | 项目隔离检查 |

同一批材料重复运行时，尽量复用已有来源和候选结果，不要不断生成重复笔记。

## 验收标准

### 单份标书

| 验收项 | 检查方法 |
|---|---|
| 要求覆盖 | 招标要求进入 `requirements.md`，每项能定位到响应章节 |
| 内容完整 | 缺失信息有明确缺口，不用猜测补齐 |
| 事实可靠 | 企业事实可追溯到 `notes/`、原始文件和原文位置 |
| 状态正确 | `candidate`、`needs-review`、`superseded` 和 `archived` 不进入正式答案 |
| 格式合规 | 章节、顺序、标题、表格和附件通过检查 |

### 多项目并行

| 验收项 | 检查方法 |
|---|---|
| 项目独立 | 标书 A 不包含项目 B 的客户名、金额和参数 |
| 内容复用 | 相同的企业资质和技术能力来自同一条已确认笔记 |
| 更新可追踪 | 更新知识笔记后，重新检索、记录影响范围并重新验收 |
| 失败可恢复 | 删除索引或中间结果后，可以从原始资料和 Markdown 重新运行 |

## 关键收益

| 维度 | 当前做法 | 打通后 |
|---|---|---|
| 资料入口 | 假设材料已经整理好 | 原始材料可以直接进入 `inbox/` |
| 知识复用 | 每次重新判断 | 已确认内容可以重复引用 |
| 事实可靠 | 依赖复制粘贴和记忆 | 保留状态、来源和原文位置 |
| 缺口处理 | AI 容易自动补全 | 明确列出缺口，等待确认 |
| 多项目并行 | 容易串客户、金额和承诺 | 项目工作区隔离并自动检查 |
| 技术升级 | 先上复杂检索系统 | 先目录和全文搜索，真实需要时再加向量或 RAG |

第一阶段先使用目录、标题、属性、链接和全文搜索。只有真实查询反复找不到内容时，才增加向量检索或 RAG。向量索引是可以重建的搜索辅助物，Markdown 和原始文件仍然是事实基础。

## 下一步

1. 选一份真实招标文件和一批混乱企业材料；
2. 招标文件放入 `work/<具体项目>/`，企业材料放入 `company-vault/inbox/`；
3. 运行一次内容盘点，检查页码、章节和表格位置是否可追踪；
4. 生成候选笔记，人工确认一小批内容；
5. 建立一个真实项目的 `work/<具体项目>/`；
6. 写投标 Skill 初版，先完成检索、缺口和状态检查；
7. 人确认后再做 Word/PDF 格式转换；
8. 记录问题，继续迭代。

# 企业知识库场景：共同 Markdown 知识表达的企业实现

更新时间：2026-09-19

> 本文是企业知识库场景材料，用来验证知识库共同框架。企业目录、字段和投标规则不属于 Agentic Work Infra 的全局要求。

## 先把问题说清楚

企业知识库，不是把所有文件集中到一个地方，也不是让 Agent 把文件自动改成一堆看起来完整的笔记。

更准确的定义是：

> 企业知识库，是一套人和 Agent 都能看见、看懂、找到、核对并持续维护的企业知识文件。

本场景把共同框架落到企业资料上：

> 以 Markdown 文件承载人和 Agent 共同理解的知识；用 Frontmatter 记录笔记属性，用 Wiki 链接表达关系，用图片和附件引用保留证据位置；用 Obsidian 浏览和维护。

Word、PDF、Excel、图片和聊天记录仍然可以作为原始证据原样保留。它们不另建一套脱离 Markdown 的长期知识真相。

这里有五个判断标准：

| 标准 | 具体表现 |
|---|---|
| 看见 | 目录、文件、来源和处理状态不是黑盒 |
| 看懂 | 一篇笔记单独打开也能说明对象、结论和适用范围 |
| 找到 | 可以通过目录、标题、全文、链接和必要的属性检索 |
| 核对 | 重要结论能够回到原始文件和原文位置 |
| 维护 | 能看出谁负责、是否有效、下一次何时复查 |

正式知识笔记的属性跟随笔记写在 Frontmatter，知识关系写成 Wiki 链接，图片和附件通过链接或索引回到证据。`inbox/`、候选笔记和处理记录是企业业务中的回溯现场，不是与正式 Markdown 知识并列的第二套架构。

## 设计入口必须是混乱资料

现实中的输入通常不是整理好的 Markdown，而是一堆混在一起的 Word、扫描 PDF、Excel、图片、聊天记录和“最终版 2”。

因此，系统不能要求企业先把资料整理好，才能进入知识库。原始资料允许很乱，`inbox/` 是一种正式状态，不是失败区。

一个 200 页的 Word 可以这样处理：

1. 原文件原样放入 `inbox/`，不覆盖、不改写、不删除；
2. Agent 盘点目录、章节、表格和可能的内容类型；
3. 标出可能属于资质、业绩、技术能力或项目要求的片段；
4. 在 `inbox/` 中生成候选笔记，并记录页码、章节或表格编号；
5. 人核对事实、适用范围和有效性；
6. 只有确认后的内容才进入 `notes/`，未确认内容继续保留候选状态。

整理失败不能导致原始资料丢失，识别不确定也不能被写成确定事实。

## 最小目录

知识库的核心结构只需要三层：

```text
company-vault/
├── inbox/       # 原始输入和候选结果，允许混乱
├── notes/       # 已确认、可复用的知识
└── archive/     # 已确认失效或被替代的知识内容
```

可以有一份说明文件记录用途和边界，但它不是知识库能够工作的前提。`sources/` 也不是必须单独建立的目录，原始文件和候选笔记可以一直保留在 `inbox/`。正式笔记失效时进入 `archive/`，原始证据不因笔记过期而移动或删除。笔记中的 `source` 一律使用 `company-vault/` 根目录相对路径；`source_location` 写成页码、章节、表格、工作表行号或消息时间等可复核定位。

项目工作区和企业知识库放在同一业务根目录下，彼此并列：

```text
business-root/
├── company-vault/
│   ├── inbox/
│   ├── notes/
│   └── archive/
└── work/
    └── 2026-餐饮投标-A客户/
        ├── project.md              # 客户、金额、工期和项目边界
        ├── requirements.md         # 招标要求
        ├── selected-notes.md       # 本项目引用了哪些企业笔记
        ├── draft/                  # 草稿
        └── output/                 # 最终交付
```

企业知识可以被项目引用。客户名、金额、工期、临时承诺和本次招标要求只能留在项目工作区。项目完成后，经过确认、允许复用的案例和经验，才重新整理成企业知识。

## 知识形成是一条可回退的流程

知识库不是“文件丢进去，AI 整理出来”这么简单。它更像一条每一步都留痕的处理流程：

```text
原始文件
  ↓
内容盘点
  ↓
候选片段
  ↓
候选笔记
  ↓
事实核对
  ↓
正式知识
```

每一步都要保留上一步的结果：

- 原始文件是不可替代的输入；
- 内容盘点说明 Agent 看到了什么；
- 候选片段说明它准备使用哪一段；
- 候选笔记是可以修改或丢弃的中间结果；
- 正式知识才允许作为跨项目复用的依据。

这样，解析错了可以重新解析原件，候选笔记错了可以删除候选结果，正式知识过期了也能找到来源和替代关系。

## 状态要比“填满字段”更重要

资料在不同阶段允许有不同状态：

| 状态 | 含义 | 能否作为正式答案 |
|---|---|---|
| `unknown` | 还不知道它是什么或是否可用 | 不能 |
| `candidate` | Agent 生成了候选结果，等待核对 | 不能 |
| `needs-review` | 发现冲突、缺字段或有效性不明 | 不能 |
| `verified` | 已由人或明确规则核对 | 有效期和适用范围也满足时可以 |
| `superseded` | 已被新版本替代 | 不能 |
| `archived` | 已确认失效或不再使用 | 不能 |

“未知”是合法状态。比如无法判断 2023 年的证书是否仍有效，应记录为 `needs-review`，不能猜成 `active`。

## Frontmatter 逐步增加

Frontmatter 不是每篇文件都必须填写的表格，而是当某个字段开始影响检索、判断或维护时，才把它显式化。

原始资料可以没有 Frontmatter。系统只需要记录文件名、进入时间、原始路径和文件类型等基础信息。

候选笔记只需要记录状态和来源：

```yaml
---
state: candidate
source: inbox/企业材料-最终版2.docx
source_location: page=43; table=项目业绩表
---
```

确认后的笔记再增加真正有用的字段：

```yaml
---
state: verified
type: 业绩案例
source: inbox/企业材料-最终版2.docx
source_location: page=43; table=项目业绩表
owner: 市场部
valid_to: 2027-12-31
---
```

没有证据的字段留空或标为未知，不能让 Agent 为了让文件“看起来完整”而猜值。`verified` 不代表永不过期：有效期已过的内容不能进入正式答案；需要时效判断却没有有效期的内容先保持 `needs-review`。

## Obsidian、Markdown、向量检索和 RAG 各自做什么

Obsidian 是本地 Markdown 的观察和人工维护界面。它适合浏览目录、编辑笔记、查看链接和反向链接，但不负责判断企业事实是否正确，也不负责保证 Agent 的回答正确。

原始文件保存证据，经过确认的 Markdown 笔记保存可以复用的结论。两者共同构成事实基础。Git、全文索引、向量索引和 RAG 都可以围绕这些文件增加，也都可以删除后重建。

检索按真实问题逐步增加：

1. **目录、标题和链接**：人通过 Obsidian 浏览，Agent 按路径读取；
2. **全文搜索**：用 Obsidian 搜索或 `rg` 找名称、编号、客户和原文句子；
3. **属性过滤**：按 `state`、`type`、`owner`、`valid_to` 缩小范围；
4. **向量检索**：当用户说法和笔记用词不同，关键词经常找不到时，按含义寻找相近内容；
5. **RAG**：先检索笔记和来源，再把检索结果交给模型生成回答。检索可以来自全文、关键词、混合检索或向量检索，RAG 不等于必须使用向量数据库。

向量知识库只是搜索辅助物，不是知识本身。RAG 只是一次“查找资料并回答”的过程，不是新的事实来源。两者都不能替代人能直接查看的 Markdown 和原始文件。

## LLM Wiki 和本体论应该放在什么位置

LLM Wiki 带来的启发，是让 Agent 把资料持续整理成可浏览、可链接、可维护的 Markdown Wiki。它降低了入口门槛，但没有取消来源、状态和维护责任。

本体论可以先用一句人话理解：企业里有哪些东西，它们之间是什么关系。第一阶段不需要正式建模，只要把常用对象说清楚，例如企业、资质、业绩、人员、产品和来源。文件夹负责浏览，属性负责过滤，Markdown 链接负责表达来源、适用、替代和冲突。

只有这些方法已经无法表达真实业务关系时，才考虑知识图谱或正式本体设计。

## 失败安全和可降级

系统应当在高级组件失效时继续工作：

```text
Obsidian 链接失效
→ 仍然可以直接打开 Markdown 文件

全文索引不可用
→ 仍然可以用 rg 搜索

向量检索不可用
→ 仍然可以用关键词、目录和链接检索

Agent 整理失败
→ 人仍然可以直接编辑笔记

Skill 执行失败
→ 原始资料和已有笔记不丢
```

因此需要遵守几条硬约束：

- 不覆盖、不删除原始资料；
- 中间结果保留，失败时返回状态和原因；
- 同一批资料重复处理，不应不断生成重复候选笔记；
- Agent 只修改被授权的目录；
- 索引、脚本和向量数据都可以重建；
- 查询遇到未知或冲突时，明确报告缺口，不自动补全。

## 第一阶段验收

先用真实资料和真实问题验证：

1. 人能否在两分钟内找到正确笔记；
2. Agent 能否找到正确笔记并给出原始来源和位置；
3. 一篇笔记离开原始文件后能否独立理解；
4. 候选和待确认内容是否不会混入正式答案；
5. 项目变量是否留在项目工作区；
6. 重复运行整理流程是否不会不断制造重复笔记；
7. 修改是否能在 Git diff 中看清；
8. 没有答案时，Agent 是否会诚实地说没有找到。

这些问题没有跑通之前，不急着增加向量数据库、知识图谱或复杂 RAG。

## 本场景结论

> 在企业场景里，先把知识建设成一套能够接住混乱输入、逐步形成可靠知识、允许人和 Agent 共同维护，并且在自动化失败时仍然可以接管的本地 Wiki。只有真实使用暴露出检索问题时，才逐步增加全文索引、向量检索或 RAG。这个结论用于企业场景，不替代知识库的共同框架。

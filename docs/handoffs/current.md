# 当前研究 Handoff

中文 | [English](current.en.md)

## 一句话结果

知识管理、媒体生产和软件开发已经成为三条独立方法线路；媒体与开发各完成一个真实任务验证，并共同支持三条可继续证伪的核心候选。

## 当前问题

> 当前执行面、唯一真源与真实结果这三条核心候选，能否在第三条独立线路中继续成立，还是会被知识复用任务收窄？

当前不预设“内容管理位于知识库之上”，也不把三条线路的目录和术语拼成统一规范。下一步从知识管理的真实复用任务反向攻击核心候选。

## 已接受基线

- 模型能够完成一次任务，不代表长期工作已经形成系统。
- 公共仓只管理抽象方法、验证协议和脱敏结论；个人内容、客户材料、代码、基础设施和真实运行状态继续由本地项目拥有。
- 知识管理、媒体生产和软件开发是平级验证线路，不是已经确定的本体分类。
- 单条线路的经验只能修改该线路；至少两条独立线路支持后，才有资格形成跨领域候选。
- “适用于所有行业”是持续接受反例的方向，不是有限案例能够证明的事实。
- 媒体与开发共同支持的最小部分只有：可替换的当前执行面、一个事实一个权威所有者、正式入口与可检查结果共同证明完成。
- 领域特有规则继续留在线路；人工发布门、渠道衍生规则、开发变更门和三面调试法都没有进入核心。

## 当前线路

1. **知识管理**：原 `knowledge-base-infra` 方法已整体迁入，当前保持 `v0.2-candidate`，不自动晋升为核心规范。
2. **媒体生产**：已迁入 Agent 协作媒体生产方法，并用一项已完成的系列内容任务验证正文真源、渠道衍生、发布授权与反馈回流；真实内容继续留在个人媒体仓。
3. **软件开发**：已迁入开发治理与调试交付方法，并用一项已完成的单用途服务任务验证现场真源、正式入口、回归边界与反馈回写；开发和产品仓继续独立。

投标/FDE 当前作为知识管理和专业交付的本地真实场景，不单独创建尚无独立方法的空线路。

## 下一动作

从知识管理线路选择一次已经发生的真实复用任务，按 `docs/validation-protocol.md` 形成第一份独立验证记录。重点攻击三个问题：当前执行面是否真有必要，唯一真源是否会与稳定对象关系冲突，技术写入完成与业务复用成功是否需要两种不同终态。

验证结束必须逐条决定核心候选是保留、收窄还是删除；不为了凑齐三条线路宣布通过，也不复制客户材料或业务知识。

## 暂不决定

- 三条线路的共同部分是生命周期、责任协议、工作连续性，还是多个不同问题。
- 最终交付是否需要 Skill、机器可判定协议或可视化工作台。
- 当前三条核心候选是否应合并为一个工作连续性协议，还是保持互相独立。

这些问题由真实案例决定，不在验证开始前锁死。

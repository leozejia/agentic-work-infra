# 当前研究 Handoff

## 一句话结果

公共仓已经形成知识管理、媒体生产和软件开发三条非空验证线路；下一步逐条从真实任务提炼证据，只有跨线路成立的约束才进入核心候选。

## 当前问题

> 一项工作要跨会话、跨工具和跨团队持续推进，最少必须保存和传递什么？

当前不预设“内容管理位于知识库之上”，也不把三条线路已有方法拼成通用规范。需要先用相互独立的真实任务验证它们是否共享同一种工作结构。

## 已接受基线

- 模型能够完成一次任务，不代表长期工作已经形成系统。
- 公共仓只管理抽象方法、验证协议和脱敏结论；个人内容、客户材料、代码、基础设施和真实运行状态继续由本地项目拥有。
- 知识管理、媒体生产和软件开发是平级验证线路，不是已经确定的本体分类。
- 单条线路的经验只能修改该线路；至少两条独立线路支持后，才有资格形成跨领域候选。
- “适用于所有行业”是持续接受反例的方向，不是有限案例能够证明的事实。

## 当前线路

1. **知识管理**：原 `knowledge-base-infra` 方法已整体迁入，当前保持 `v0.2-candidate`，不自动晋升为核心规范。
2. **媒体生产**：已明确通用方法与个人内容的边界；真实内容继续留在个人媒体仓。
3. **软件开发**：已明确开发治理、真实 E2E 与具体基础设施的边界；开发和产品仓继续独立。

投标/FDE 当前作为知识管理和专业交付的本地真实场景，不单独创建尚无独立方法的空线路。

## 下一动作

先推进媒体生产线路：选择一个已经完成的真实选题，从信号、来源、作者判断、正文、渠道衍生物、人工发布到后续反馈，还原实际链路。按 `docs/validation-protocol.md` 完成续接、真源、结果和反馈测试，只记录能够公开的最小证据，不修改或复制个人内容。

媒体线路形成第一份验证结论后，再用软件开发中的一个真实项目按同一协议验证。完成两条独立线路前，不创建 `core/`。

## 暂不决定

- 核心管理单元最终叫工作资产、工作对象、上下文还是其他名称。
- 三条线路的共同部分是生命周期、责任协议、工作连续性，还是多个不同问题。
- 最终交付是否需要 Skill、机器可判定协议或可视化工作台。

这些问题由真实案例决定，不在验证开始前锁死。

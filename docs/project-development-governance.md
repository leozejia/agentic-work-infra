# 项目开发治理规范

更新时间：2026-07-17

这份文档规定跨项目开发时如何守住用户目标、控制系统复杂度、管理项目真相并完成真实交付。它是项目治理母版，不是具体项目的运行手册；项目需要长期执行的规则，应写进项目自己的 `AGENTS.md`、产品文档或架构文档。

## 1. 从一句话用户结果开始

每个产品和里程碑都必须能用一句话说明用户最终得到什么。目标描述结果，不描述模块、页面、Agent 数量或实现步骤。

开始实现前至少明确：

- 用户是谁；
- 用户提供什么；
- 系统交付什么可检查结果；
- 哪些风险或决定必须交给人；
- 当前明确不做什么。

如果一个改动无法解释它如何直接服务这句话目标，就不应进入当前里程碑。实现过程中发现目标已经改变，应停止扩展，先更新产品事实和验收标准。

## 2. 项目真相必须分层

聊天、运行日志和旧 handoff 都不能成为长期真相。一个项目应明确以下职责：

```text
AGENTS.md
  短而稳定的项目宪法、不可违背原则和读文档顺序

docs/product/
  用户、产品目标、行为边界和成功标准

docs/architecture/
  长期技术边界、正式状态和所有权

docs/handoffs/current.md
  当前里程碑、已接受基线、下一动作和停止点

docs/operations/
  构建、安装、发布、恢复和真实环境入口

docs/archive/
  已完成或失效的过程记录
```

规则只保留一个权威来源。其他文档可以链接，不能复制后各自演化。外部技能包、个人习惯和聊天约定都不是项目约束；真正需要执行的规则必须写回项目内。

## 3. 使用最小充分正确的设计

治理目标不是最少代码，也不是最大抽象，而是当前阶段下边界正确、成本可控、能够真实交付的设计。

新增以下任何结构前，必须经过架构变更门：

- 持久状态或数据表；
- fallback 或兼容层；
- 工作流、状态机、队列或后台服务；
- 新的内部 Agent、运行时或协议；
- 框架、插件系统或通用抽象。

变更门只问五个问题：

1. 它解决了哪个已经发生的用户问题或维护问题？
2. 引入后，谁是唯一真相源和唯一写入者？
3. 官方能力、平台能力或现有结构为什么不能完成？
4. 不实现它会造成什么可观察的真实损失？
5. 用什么真实验收证明它必要且正确？

回答依赖“以后可能需要”“更完整”“更工程化”或“加一层更安全”，不足以通过。

## 4. 官方能力优先

先确认标准库、平台原生能力、官方 Agent、官方协议和现有依赖是否已经提供正确路径。只有官方路径确实无法满足产品契约时，才增加项目自有机制。

围绕强能力再造一套运行时、权限模型、重试状态机或输出协议，通常同时增加故障点和认知成本。项目更适合治理输入、正式产物、不可逆写入和人类决定，而不是限制工具的正常推理与执行过程。

## 5. 正式状态与临时控制必须分开

每类事实只允许一个正式所有者。用户文件、已确认决策、正式业务数据和交付产物可以成为持久真相；下面这些默认只是临时控制面：

- 候选项和待处理项；
- Agent 输出流和运行日志；
- 页面加载、忙碌和进度状态；
- scratch、缓存、中间文件和预览；
- 尚未确认的推断和建议。

临时状态不得反向覆盖正式内容，也不得因为 UI 需要展示而升级成第二套业务模型。确需持久化时，必须说明生命周期、清理规则、唯一写入者和恢复语义。

## 6. 里程碑治理

中长任务使用一个当前 handoff 管理，不用聊天承担项目状态。Handoff 应包含：

- 一句话产品结果；
- 当前里程碑和非目标；
- 已经接受的基线；
- 尚未接受的部分；
- 下一项精确动作和停止点；
- 验收证据；
- 分支、工作树和提交状态。

Handoff 是当前执行面板，不保存完整历史。完成或失效后归档；长期规则先写入产品或架构文档，再由 handoff 引用。

计划优先定义目标、边界、完成条件和审核点。只有存在严格顺序、高风险操作或真实协作冲突时，才拆成细任务。不要用清单替代高阶 Agent 的判断。

## 7. 实现与审查纪律

实现前读取项目权威文档和工作树状态，未知修改默认属于用户或其他任务。每个 diff 文件都必须能从当前目标解释，不能顺手清理、迁移或重构无关模块。

审查优先检查：

- 是否仍然服务原始用户结果；
- 是否新增了第二真相源；
- 是否用 fallback 掩盖失败；
- 是否把内部状态暴露成产品概念；
- 是否因为假想未来引入抽象；
- 是否具备旧实现失败、新实现通过的行为证据；
- 是否走过对应的真实运行环境。

实现者可以完成窄测试，但不能只凭自己的解释宣布复杂改动完成。高风险或跨边界变更应由独立 Reviewer 按用户结果和触发条件审查。

## 8. 必须停止局部补丁的信号

出现以下任一情况，停止继续叠加条件，回到目标、真相源和责任边界重新设计：

- 同一用户症状修复后再次出现；
- 一个缺陷需要新增多个持久状态才能解释；
- fallback、兼容逻辑或恢复逻辑进入正常主路径；
- 多个模块维护同一业务事实；
- UI 需要向用户解释大量内部状态；
- 修复范围持续扩大，却没有更接近用户交付物；
- 测试只能证明实现细节，不能证明用户结果。

正确的重构通常会删除错误抽象或合并所有权，而不是给它增加更多守卫。

## 9. 真实交付才算完成

验证按成本逐级进行，但接受产品能力必须回到真实路径：

```text
静态检查
  -> 最小行为回归
  -> 构建或安装态
  -> 正式产品入口
  -> 真实数据和真实环境
  -> 用户可检查交付物
```

Mock、fixture、源码字符串断言、演示项目和 fallback 只适合快速反馈，不能作为产品完成证据。失败、等待、部分结果和环境限制必须诚实呈现，不能包装成成功。

完成意味着：用户能通过正式入口获得目标结果；关键风险可见；正式状态可审计；下一位工程师不依赖聊天也能继续。

## 10. 项目宪法写作边界

项目 `AGENTS.md` 应短、稳定、自洽，通常只包含：

- 项目是什么、不是什么；
- 权威文档读序；
- 产品与架构不变量；
- 高风险禁区；
- 验证入口。

不要放历史、截图、测试输出、长命令、一次性 handoff 或尚未定型的方案。修改前只问一个问题：这条规则三个月后仍然需要每位工程 Agent 执行吗？如果不是，就放到更合适的文档或不写。

## 11. 里程碑检查

开始前：

- 一句话用户结果和非目标已经明确；
- 已读取正式真相源和当前 handoff；
- 没有把外部习惯当成项目规则；
- 已确认官方或现有能力不能直接解决问题。

提交前：

- 每个文件都能从目标解释；
- 没有新增未经变更门证明的状态、fallback 或抽象；
- 正式状态只有一个所有者；
- 最终 diff 上跑过对应验证；
- 文档、实现和真实行为一致。

接受前：

- 正式入口、真实环境和真实数据已经验证；
- 用户可以检查最终结果；
- 未完成部分被明确标记，没有伪装成功；
- 当前 handoff 已收口，长期规则已回到权威文档。
